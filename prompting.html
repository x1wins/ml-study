💬 Prompt Engineering

The cheapest, fastest way to get better answers from an LLM — before you ever reach for RAG or fine-tuning.

1. What is a prompt?

A prompt is the text you send to a language model. The model predicts the most likely continuation, so the words you choose steer everything. Prompt engineering is the craft of writing inputs that reliably produce the output you want.

Why it matters: The same model can give a vague, wrong answer or an excellent, structured one — purely based on the prompt. No retraining, no servers, no cost. It's the highest-leverage skill when working with LLMs.

2. Anatomy of a good prompt

Strong prompts usually contain some of these building blocks:

  • Role / persona — "You are an expert Python reviewer."
  • Task — a clear, specific instruction (one main goal).
  • Context — the data, background, or constraints it needs.
  • Format — how the answer should look (JSON, bullet list, table, length).
  • Examples — show the pattern you want (see few-shot below).
Vague ✗: Tell me about databases.
Specific ✓: You are a senior backend engineer. In 5 bullet points, explain when to choose PostgreSQL over MongoDB for a transactional app. Keep each bullet under 20 words.
Rule of thumb: be specific. Say who the model is, exactly what you want, and the exact shape of the answer. Ambiguity is the #1 cause of bad outputs.

3. Zero-shot, One-shot, Few-shot

"Shots" = how many worked examples you put in the prompt before the real task.

StyleExamples givenBest for
Zero-shot0Simple, common tasks the model already knows
One-shot1Showing a specific format once
Few-shot2–5Teaching a pattern, tone, or edge cases

Few-shot example — teaching a sentiment label format:

Classify the sentiment as POSITIVE, NEGATIVE, or NEUTRAL.

Review: "The battery lasts forever!"      → POSITIVE
Review: "It broke after two days."        → NEGATIVE
Review: "It arrived on Tuesday."          → NEUTRAL
Review: "Best purchase I've made — wow."  →
Why it works: the examples show the model the exact input→output pattern, so it copies the shape (labels only, uppercase) instead of writing a paragraph.

4. System / User / Assistant roles

Chat LLMs accept messages tagged with a role. Using them well separates persistent instructions from the current question.

  • system — sets behavior, rules, persona (applies to the whole chat)
  • user — the actual question/request
  • assistant — the model's replies (and prior turns for context)
[
  {"role": "system",
   "content": "You are a terse SQL tutor. Answer with a query first, then one line of explanation."},
  {"role": "user",
   "content": "How do I get the 3 most recent orders per customer?"}
]
Why it matters: put durable rules (tone, format, guardrails) in system so they persist across the conversation, instead of repeating them in every user message.

5. Chain-of-Thought (think step by step)

For reasoning, math, or multi-step tasks, ask the model to work through steps before answering. This "chain-of-thought" often dramatically improves correctness.

✗ What's 17 × 24? Give the number. — may guess.
✓ What's 17 × 24? Think step by step, then give the final number on its own line.
Tip: if you don't want the reasoning shown to end users, ask it to reason internally and output only the final answer — or use a model that hides its reasoning. Simple triggers: "Let's think step by step."

6. More techniques

  • Specify the output format — "Respond as JSON with keys title and tags." Great for parsing programmatically.
  • Give constraints — length, audience, reading level, what to avoid.
  • Delimit inputs — wrap pasted text in triple quotes or tags so the model knows data from instructions: Summarize the text between <doc></doc>.
  • Ask for a plan first — "Outline your approach, then execute."
  • Let it say "I don't know" — "If the text doesn't contain the answer, say so." Reduces made-up answers.
  • Iterate — treat prompting as a loop: try, inspect, refine.
Format tie-in: when you need strict output every time (always valid JSON, a fixed schema), that's a signal you may want fine-tuning; prompting gets you most of the way first.

7. Common pitfalls

PitfallFix
Vague / open-ended asksBe specific: role + task + format
Multiple tasks in one promptSplit into steps or separate prompts
Mixing instructions with pasted dataDelimit the data (tags / quotes)
Expecting fresh/private facts it never sawUse RAG to supply them
Assuming it can do exact mathChain-of-thought, or call a tool/calculator
Trusting confident answersAsk for sources; verify; allow "I don't know"
Hallucination note: a fluent, confident answer can still be wrong. Prompts that allow "I'm not sure" and request citations reduce (but don't eliminate) this. For factual grounding, add RAG.

8. The ladder: Prompting → RAG → Fine-tuning

When prompting alone isn't enough, climb the ladder — but only as far as you need. Each rung adds power and cost/complexity.

RungUse whenCost
PromptingReshaping behavior with instructions/examplesFree, instant
RAGThe model needs your facts / fresh dataLow setup
Fine-tuningYou need consistent behavior/format/skill at scaleHigh setup
Need better output? → Prompt first. Need knowledge? → RAG. Need behavior? → Fine-tune.
Golden rule: exhaust prompting before RAG, and RAG before fine-tuning. Most problems are solved on the lowest rung — and it costs nothing to try.
