1. The Problem RAG Solves

A trained model is a snapshot in time. That snapshot creates three headaches.

Why a plain LLM falls short

  • Frozen knowledge — it only knows what existed before its training cutoff. Ask about last week and it guesses.
  • No private data — your company wiki, contracts, and support tickets were never in its training set.
  • Hallucination — when it doesn't know, it often invents a confident, wrong answer instead of saying "I don't know".
The open-book-exam analogy: A closed-book exam forces you to recall everything from memory — and you'll bluff on questions you forgot. An open-book exam lets you look up the exact page first, then answer. RAG turns the LLM's closed-book exam into an open-book one: retrieve the relevant pages, hand them to the model, then ask the question.

2. The RAG Pipeline

RAG has two phases: indexing (done once, ahead of time) and query (done every time a user asks something).

Phase A — Indexing (build the searchable library)

  1. Load your documents (PDFs, wiki pages, docs).
  2. Chunk them into small passages (a few hundred tokens each).
  3. Embed each chunk into a vector (a list of numbers capturing its meaning).
  4. Store the vectors in a vector database for fast similarity search.

Phase B — Query (answer a question)

  1. Embed the question with the same embedding model.
  2. Similarity search — find the chunks whose vectors are closest to the question's vector.
  3. Augment the prompt — paste those chunks into the prompt as context.
  4. Generate — the LLM answers using that context and cites the sources.
Key insight: the LLM is never retrained. RAG changes the input (what context we feed it), not the model's weights. Update your documents and answers update instantly — no training required.

3. Embeddings & Cosine Similarity

The trick that lets a computer find text "about the same thing" without matching exact words.

What is an embedding?

An embedding is a list of numbers (a vector) that captures the meaning of a piece of text. Texts with similar meaning get vectors that point in similar directions, even if they share no words. "How do I reset my password?" and "I forgot my login credentials" land close together.

Where do embeddings come from? The same Transformer machinery that powers LLMs. See the Transformers and e / softmax pages — embeddings are the vectors flowing through those attention layers.

Cosine similarity — measuring "same direction"

To compare two vectors we measure the angle between them. Cosine similarity is the cosine of that angle: 1 means identical direction (very similar), 0 means unrelated (perpendicular), −1 means opposite.

cos(θ) = (A · B) / (‖A‖ × ‖B‖)

The dot product A · B = Σi AiBi divided by the two magnitudes ‖A‖ = √(Σi Ai²).

import numpy as np

def cosine_similarity(a, b):
    a = np.asarray(a, dtype=float)
    b = np.asarray(b, dtype=float)
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

q    = np.array([0.9, 0.1, 0.2])   # "reset password"
doc1 = np.array([0.8, 0.2, 0.1])   # "forgot login"     -> similar
doc2 = np.array([0.1, 0.9, 0.7])   # "billing invoice"  -> different

print(round(cosine_similarity(q, doc1), 3))  # 0.987  (close)
print(round(cosine_similarity(q, doc2), 3))  # 0.301  (far)
Why matters: "find the most relevant chunk" becomes "find the stored vector with the highest cosine similarity to the question vector." That single number drives retrieval.

4. End-to-End RAG in Python

A complete, minimal RAG loop: embed a few documents, retrieve the best match for a question, and build the augmented prompt.

Minimal RAG (sentence-transformers + numpy search)

Reference-only: needs pip install sentence-transformers (downloads a model on first run). The retrieval math is plain numpy — no vector DB needed for a small demo.

# reference-only: requires `pip install sentence-transformers numpy`
import numpy as np
from sentence_transformers import SentenceTransformer

# --- INDEXING (done once) ---
docs = [
    "To reset your password, open Settings and click 'Forgot password'.",
    "Invoices are billed monthly on the first day of each month.",
    "Our office hours are 9am to 5pm, Monday through Friday.",
]

model = SentenceTransformer("all-MiniLM-L6-v2")   # small, fast, CPU-friendly
doc_vecs = model.encode(docs, normalize_embeddings=True)   # shape (3, 384)

def cosine(a, b):
    # vectors are already normalized, so dot product == cosine similarity
    return float(np.dot(a, b))

# --- QUERY (each question) ---
question = "How do I change my login password?"
q_vec = model.encode(question, normalize_embeddings=True)

# similarity search: score every doc, take the best
scores  = [cosine(q_vec, d) for d in doc_vecs]
best_i  = int(np.argmax(scores))
context = docs[best_i]

# --- AUGMENT the prompt ---
prompt = f"""Answer the question using ONLY the context below.
If the answer is not in the context, say you don't know.

Context:
{context}

Question: {question}
Answer:"""

print(f"Retrieved (score={scores[best_i]:.3f}): {context}")
print("--- prompt sent to the LLM ---")
print(prompt)
# Next step: send `prompt` to your LLM (e.g. Ollama) to generate the final answer.
Practical local stack: for a private, self-hosted setup run Ollama for the LLM (e.g. ollama run llama3) and store vectors in pgvector on Postgres (great if you already run Postgres) or a dedicated store like Chroma or FAISS. The retrieved context is pasted into the prompt exactly as above — only the storage/generation backends change.

5. RAG vs Fine-Tuning

Two ways to specialize an LLM — they solve different problems. See the Fine-Tuning page for the other side.

Side-by-side comparison

 RAGFine-Tuning
What changesThe prompt (adds retrieved context)The model's weights
Best forInjecting knowledge / factsTeaching behavior, style, format, skills
Fresh dataInstant — just update documentsRequires retraining
CitationsYes — you know the source chunkNo — knowledge is baked in, opaque
HallucinationLower — grounded in retrieved textUnchanged / can still invent facts
Upfront costLow — build an indexHigh — GPUs + labeled data + training
Per-query costHigher — retrieval + longer promptLower — no retrieval step
LatencyHigher (search + bigger prompt)Lower (single forward pass)
Data neededDocuments (unlabeled)Curated input→output examples
Access controlEasy — filter which docs are retrievable per userHard — knowledge is fused into weights
Decision rule: Need knowledge → RAG. Need behavior/skill/format → Fine-tune. Need both → do both, try RAG first.

6. Chunking & Evaluation

Chunking tips

  • Size: aim for ~200–500 tokens per chunk — big enough to hold a complete idea, small enough to stay focused.
  • Overlap: let chunks overlap by ~10–20% so a sentence split across a boundary isn't lost.
  • Respect structure: split on natural boundaries (headings, paragraphs) rather than mid-sentence.
  • Keep metadata: store the source title, page, and URL with each chunk so you can cite it.
  • Match the model: use the same embedding model for indexing and querying, or the vectors won't be comparable.

Evaluating a RAG system

Two things can go wrong: retrieval finds the wrong chunks, or generation ignores the good chunks. Measure both.

MetricQuestion it answers
Context recallDid retrieval find the chunks that actually contain the answer?
Context precisionWere the retrieved chunks relevant (not noise)?
Faithfulness / groundingIs every claim in the answer supported by the retrieved context (no invented facts)?
Answer relevanceDoes the answer actually address the question?
Grounding is the whole point. A faithful answer states only what the retrieved context supports — and says "I don't know" when the context is silent. That's how RAG fights hallucination.
