1. Why privacy matters

Personal data is a liability the moment it enters your system. Handle it wrong and you risk harm to users, fines, and lost trust.

What is PII?

PII (Personally Identifiable Information) is any data that can identify a person, alone or combined with other data. It comes in two flavors:

  • Direct identifiers — name, email, phone, SSN, passport, account number, face.
  • Quasi-identifiers — ZIP code, birth date, gender, job title. Individually vague, but combined they can re-identify someone (a famous result: ZIP + birth date + gender identifies most US residents).

Some PII is sensitive (health, biometrics, race, religion, sexual orientation) and usually carries stricter handling rules.

Regulations — the high-level idea (not legal advice)

Most privacy laws share the same core principles. Knowing the shape of them helps you design systems that stay out of trouble:

  • GDPR (EU) — lawful basis to process, right to access/erasure, data minimization, breach notification.
  • CCPA/CPRA (California) — disclosure of what's collected, right to opt out of sale, right to delete.
  • HIPAA (US health) — protects health information (PHI); defines de-identification standards.
Engineering takeaway: collect less, protect what you keep, be able to find and delete a person's data on request, and never send raw PII somewhere you can't control (a third-party LLM API, an analytics log, a vector index).

2. Anonymization vs. pseudonymization

These sound similar but differ in one crucial way: whether the original data can ever be recovered.

The key distinction

  • Anonymization — irreversibly strips identifiers so no one (not even you) can link data back to a person. Done well, the data falls outside many privacy regulations because it's no longer “personal.”
  • Pseudonymization — replaces identifiers with a token or reference that can be reversed with a separately-stored key (a “mapping table” or vault). Still personal data, but safer at rest.
Anonymize → one-way (no key) · Pseudonymize → reversible (key held separately)
Why it matters: if your pipeline needs to reconnect results to a user later (e.g., “show this customer their own record”), you need pseudonymization. If you only need aggregate insight, anonymize — it's the stronger guarantee.

Common techniques

TechniqueHow it worksReversible?
Redaction / maskingReplace value with a placeholder like [EMAIL] or ****1234No
TokenizationSwap value for a random token; keep the map in a secure vaultYes (with vault)
Hashing (salted)One-way transform; same input → same hashNo (but joinable)
GeneralizationCoarsen a value (age 34 → “30–39”; ZIP 94107 → 941**)No
SuppressionDrop the field entirelyNo

Note: hashing PII is not true anonymization — if the input space is small (e.g., phone numbers), an attacker can brute-force the hash. Always salt, and prefer tokenization when you might need reversal.

3. The anonymization pipeline

The golden rule: scrub PII before text is embedded, logged, or sent to any model.

Detect → redact/tokenize → embed

A safe RAG or LLM pipeline inserts a scrubbing stage between raw input and everything downstream:

Illustrative Python-ish flow (reference — detect_entities and embed stand in for a real NER model and embedding API):

# illustrative / reference (pseudo-code, not runnable as-is)
import re

def detect_entities(text):
    """Return spans of detected PII. In production use a proper NER model
    (e.g., Presidio, spaCy) plus regex for structured IDs."""
    patterns = {
        "EMAIL": r"[\w.+-]+@[\w-]+\.[\w.-]+",
        "PHONE": r"\b\d{3}[-.]?\d{3}[-.]?\d{4}\b",
        "SSN":   r"\b\d{3}-\d{2}-\d{4}\b",
    }
    spans = []
    for label, pat in patterns.items():
        for m in re.finditer(pat, text):
            spans.append((m.start(), m.end(), label, m.group()))
    return spans

def redact(text, spans, vault=None):
    """Replace each PII span with a placeholder (or a reversible token)."""
    out = text
    for start, end, label, value in sorted(spans, reverse=True):
        if vault is not None:                 # pseudonymize
            token = vault.store(label, value) # e.g. "EMAIL_7f3a"
            replacement = f"[{token}]"
        else:                                 # anonymize (irreversible)
            replacement = f"[{label}]"
        out = out[:start] + replacement + out[end:]
    return out

# --- pipeline ---
raw = "Contact Jane at jane.doe@acme.com or 415-555-0100."
safe = redact(raw, detect_entities(raw))     # vault=None -> anonymize
# safe == "Contact Jane at [EMAIL] or [PHONE]."

vector = embed(safe)   # only the SCRUBBED text is embedded / sent to the LLM
store(vector)          # raw PII never reaches the vector DB or logs
Scrub PII before it ever reaches embeddings or logs. Once raw text is embedded or written to a log line, it's copied into places you may not fully control — and embeddings can leak the original content. Do the scrubbing at the front door, not after.

Practical notes

  • Combine NER models (names, locations, orgs) with regex (emails, phones, card numbers) — each catches what the other misses.
  • No detector is perfect. Add a human review or confidence threshold for high-risk flows, and log counts of detections, never the values.
  • Keep the det-and-redact step idempotent so re-processing the same document yields the same tokens.

4. Differential privacy & DP-SGD

A mathematical guarantee that the output barely changes whether or not any single person's record is included.

The intuition

Differential privacy (DP) adds carefully calibrated noise to results (counts, averages, gradients) so that no individual record measurably affects the output. If you can't tell whether Alice's data was in the dataset, you can't learn anything specific about Alice.

The strength is controlled by the privacy budget ε (epsilon):

smaller ε → more noise → stronger privacy (less accuracy)

Formally, a mechanism is ε-differentially private if, for any two datasets differing by one record, the probability of any output changes by at most a factor of eε:

Pr[M(D) ∈ S] ≤ eε · Pr[M(D′) ∈ S]
Budget intuition: every query spends some of your ε budget. Ask too many questions and the cumulative leakage grows — so DP systems track and cap total ε across all queries.

A tiny DP example: the noisy count

Adding Laplace noise scaled to sensitivity / ε makes a count private. Here sensitivity is 1 (adding/removing one person changes the count by 1):

import numpy as np

def private_count(true_count, epsilon, sensitivity=1.0, rng=None):
    """Return an epsilon-DP noisy count via the Laplace mechanism."""
    rng = rng or np.random.default_rng(0)
    scale = sensitivity / epsilon          # bigger epsilon -> less noise
    noise = rng.laplace(loc=0.0, scale=scale)
    return true_count + noise

# 1000 users opted in; release a private count
print(round(private_count(1000, epsilon=1.0)))   # ~1000, slightly perturbed
print(round(private_count(1000, epsilon=0.1)))   # noisier: stronger privacy

Runnable with numpy. Smaller epsilon visibly increases the noise — that's the privacy/accuracy tradeoff in action.

DP-SGD in one paragraph

DP-SGD (Differentially Private Stochastic Gradient Descent) trains models with DP guarantees. During each step it clips every example's gradient to a fixed norm (so no single record can dominate the update), then adds Gaussian noise to the summed gradients before applying them. A privacy accountant tracks the cumulative ε spent across all training steps. The result: the trained weights provably don't memorize any single training example too strongly — at the cost of some accuracy and slower training. Libraries like Opacus (PyTorch) and TensorFlow Privacy implement this.

5. Data minimization & retention

The safest data is the data you never collected. The second safest is the data you already deleted.

Principles

  • Minimize collection — only gather fields you actually use. Don't log full request bodies “just in case.”
  • Minimize scope — strip PII as early as possible; pass only what each downstream step needs.
  • Set retention — give every dataset a TTL. Auto-delete raw inputs, prompts, and logs after a defined window.
  • Support deletion — be able to find and erase one person's data (right to erasure). This is far easier when records carry stable pseudonymous IDs.

Illustrative retention policy (reference YAML):

# reference / illustrative
retention:
  raw_uploads:    { ttl_days: 7,   pii: true }
  scrubbed_docs:  { ttl_days: 365, pii: false }
  request_logs:   { ttl_days: 30,  pii: false }  # never log raw PII
  vector_index:   { ttl_days: 365, pii: false }  # scrubbed text only

6. PII leakage: embeddings, logs, memorization

PII escapes in subtle ways. These three are the most common in ML/LLM systems.

Three leakage vectors

  • Embeddings — a vector is a lossy but often invertible representation. Research shows text can be partially reconstructed from embeddings. Treat embeddings of raw PII as sensitive as the PII itself — so scrub first.
  • Logs & traces — prompts, request bodies, and error stack traces routinely capture user text. These flow into observability tools, backups, and third parties. Redact before logging.
  • Model memorization — large models can memorize and later regurgitate rare training strings verbatim (an SSN, an API key). Fine-tuning on raw user data risks this; DP-SGD and de-duplication reduce it.
Why it matters: a vector store or log pipeline is often less locked-down than your primary database, yet it can hold the same PII. The scrub-at-the-front-door rule closes all three vectors at once.

7. Comparison of techniques

TechniqueWhat it protectsTradeoff
Redaction / masking Removes direct identifiers from text before embed/log Irreversible; loses context; detector misses leak through
Tokenization (pseudonymize) Hides PII while keeping ability to re-link via a vault Vault is a new secret to secure; still “personal data”
Generalization / k-anonymity Blurs quasi-identifiers so records aren't unique Reduces data granularity; vulnerable to linkage attacks
Differential privacy Provable per-individual guarantee on released stats Noise reduces accuracy; must manage ε budget
DP-SGD Limits what trained model weights can memorize Slower training; accuracy drop; tuning clip norm & noise
Data minimization / retention Shrinks the amount & lifetime of PII at risk May limit future analytics; needs deletion tooling
In practice, layer them: scrub at ingest (redact/tokenize), minimize what you keep, add DP for released aggregates, and use DP-SGD if you fine-tune on user data. No single technique is sufficient alone.
