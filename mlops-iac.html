🏗️ Infrastructure as Code (IaC) for ML

Spin up GPU training environments, storage, and networking from version-controlled files — then tear it all down to stop the bill. Reproducible infra instead of clicking around a console.

1. What IaC is & why it matters

Infrastructure as Code = describing servers, storage, and networks in text files that a tool reads and provisions for you.

Clicking in a console vs. writing code

When you set up a GPU instance by clicking through a cloud console, the result lives only in that account — nobody can review it, reproduce it, or roll it back. With IaC you write a file like main.tf that declares what you want, commit it to git, and the tool makes reality match the file.

AspectClicking in a consoleInfrastructure as Code
ReproducibleNo — manual, error-proneYes — same files, same result
Version-controlledNo historyEvery change in git, reviewable in a PR
TeardownHunt & delete by handOne command destroys everything
Team sharing"How did you set that up?"Clone the repo & apply
Why it matters for ML: a training run is only reproducible if the environment is reproducible too. IaC pins the instance type, region, disk size, and drivers so a teammate (or future you) gets the exact same GPU box.

The core idea: declarative & idempotent

You describe the desired end state, not the steps. Running the same file twice does not create two buckets — the tool checks what already exists and only changes the difference. That property is called idempotency.

your files (desired state) − current cloud (actual state) → the changes to apply

2. Terraform vs CloudFormation

The two most common IaC tools you will meet. Both are declarative; they differ in scope and how they track state.

Side by side

 Terraform (HashiCorp)CloudFormation (AWS)
Cloud supportMulti-cloud via providers (AWS, GCP, Azure…)AWS only
LanguageHCL (HashiCorp Configuration Language)YAML or JSON templates
StateA terraform.tfstate file you manage (often in S3)Managed by AWS behind the scenes
StyleDeclarativeDeclarative
EcosystemHuge module registryTight AWS integration
Which to learn first? Terraform — its multi-cloud providers and readable HCL make it the default for ML platform work, and the concepts transfer everywhere.

Three words you must know

  • Declarative — you state the goal (“one GPU instance”), the tool figures out the how
  • Providers — plugins that teach Terraform how to talk to AWS, GCP, Azure, etc.
  • State — a record of what Terraform has created, so it knows what to change or destroy next time
# reference: declare the AWS provider and region (Terraform HCL)
terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}

provider "aws" {
  region = "us-east-1"
}

Snippet is reference only — it targets a real AWS account and cannot run in this browser.

3. Spinning up an ML training environment

A minimal training setup needs three things: a GPU instance to train on, a storage bucket for data & artifacts, and networking to connect them.

The three pieces

  • Compute — a GPU instance (e.g. AWS g5/p4d) where training actually runs
  • Storage — an S3 bucket holding the dataset going in and the model checkpoints coming out
  • Networking — a VPC, subnet, and security group so the instance can reach S3 and you can reach the instance

Illustrative Terraform: a GPU box + an S3 bucket

The snippet below declares one GPU instance and one bucket. It is illustrative — it targets real AWS resources (and real charges) and cannot run in this browser. Names, AMI, and instance type would be filled in for your account/region.

# illustrative — Terraform HCL (targets real AWS, do not run as-is)

# GPU compute for training (g5 = NVIDIA A10G)
resource "aws_instance" "trainer" {
  ami           = "ami-0abcd1234gpu"   # a deep-learning AMI with drivers
  instance_type = "g5.xlarge"          # 1 GPU — adjust to your job
  subnet_id     = aws_subnet.train.id

  tags = {
    Project = "ml-study"
    Purpose = "training"
    Owner   = "you"
  }
}

# Storage for datasets and model artifacts
resource "aws_s3_bucket" "artifacts" {
  bucket = "ml-study-artifacts-demo"

  tags = {
    Project = "ml-study"
    Purpose = "data-and-artifacts"
  }
}
Why tag everything? Tags like Project and Owner let you find, group, and bill ML resources — and quickly spot orphaned GPUs someone forgot to destroy.

4. Managing training clusters (autoscaling & spot)

One instance is fine for a small job. For bigger or many parallel jobs, you scale to a cluster — and you make it cheap with spot/preemptible instances.

Autoscaling groups

An autoscaling group (ASG) keeps a target number of instances running and can grow or shrink on demand. For training you often set min = 0 so the group scales all the way down to zero when idle — no idle GPUs, no idle bill.

# illustrative — Terraform HCL (AWS autoscaling group)
resource "aws_autoscaling_group" "trainers" {
  min_size         = 0     # scale to zero when idle (no cost)
  max_size         = 8     # burst up to 8 GPU nodes
  desired_capacity = 0

  tag {
    key                 = "Project"
    value               = "ml-study"
    propagate_at_launch = true
  }
}

Spot / preemptible instances = cheap training

Cloud providers sell spare capacity at a steep discount: AWS calls it Spot, GCP calls it preemptible/Spot. The catch: the provider can reclaim the machine with a couple minutes’ notice. That is fine for training if you checkpoint often to S3, so a reclaimed job resumes instead of restarting.

Instance typePriceCan be reclaimed?Good for
On-demandFull priceNoServing, short critical jobs
Spot / preemptibleUp to ~70–90% cheaperYes, with short noticeFault-tolerant training with checkpoints
Rule of thumb: train on spot + frequent checkpoints, serve on on-demand. You get GPU training at a fraction of the cost with little downside.

5. The plan / apply / destroy lifecycle

Terraform’s workflow is three commands. Learn these and you can drive any infrastructure.

The three commands

CommandWhat it does
terraform planDry run — shows exactly what will be created, changed, or destroyed. No changes made.
terraform applyMakes the cloud match your files. Creates the GPU box, bucket, network.
terraform destroyDeletes everything Terraform created. Your bill stops.
# reference — CLI (needs a configured cloud account)
terraform init      # download providers, set up state
terraform plan      # preview the changes (safe, read-only)
terraform apply     # build the environment
# ... run your training job ...
terraform destroy   # tear it all down when done
Always plan before apply. The plan output is your safety check — it lists every resource that will be created or destroyed, so you never get a surprise GPU (or lose one you needed).

6. Teardown to save cost

The single most important cost habit in ML: destroy what you are not using.

Destroy when the job is done

Because the environment is code, tearing it down is one command — not a scavenger hunt through the console. Wrap it into your workflow: apply, train, download artifacts, destroy.

# reference — CLI
terraform destroy -auto-approve   # remove the GPU box + network
# S3 artifacts persist if you keep the bucket — storage is cheap, GPUs are not
Never leave GPUs running. An idle GPU instance costs the same as a busy one — and a single large multi-GPU box can burn tens of dollars per hour, day and night, whether or not a job is running. Forgetting one over a weekend is a classic, expensive mistake. Destroy (or scale the ASG to zero) the moment training finishes; keep only the cheap S3 artifacts.

Cheap habits that add up

  • Set autoscaling min_size = 0 so idle clusters cost nothing
  • Train on spot/preemptible instances with frequent S3 checkpoints
  • Tag every resource so you can find and kill orphans by Project/Owner
  • Run terraform destroy as the last step of every experiment
  • Keep artifacts in cheap object storage, not on running GPU disks
