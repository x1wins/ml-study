📦 Model Registry & Versioning

Which model, data, and params produced this result? Track experiments, version datasets, and promote models to production — so every result is reproducible.

1. The Problem: Reproducibility

A model result is only trustworthy if you can recreate it. That means pinning down everything that went into it.

Why "it works" is not enough

Say your model hits 94% accuracy. Great — but three questions immediately follow:

  • Which code? Which git commit of the training script and feature pipeline?
  • Which data? Which snapshot of the dataset (rows added/removed since)?
  • Which params? Learning rate, epochs, seed, model architecture?
  • Which weights? The exact serialized artifact that scored 94%?

If you cannot answer all four, you cannot reproduce the result, debug a regression, or roll back safely. Manual tracking in a spreadsheet breaks down fast.

Why it matters: Reproducibility is the foundation of trust, debugging, audits, and safe rollbacks. Regulators, teammates, and future-you all need to trace a live prediction back to the exact inputs that created the model.

A model is code + data + params + weights

Unlike a normal software artifact (just code), a trained model is the product of four moving parts. Change any one and you get a different model.

model = f( code · data · params ) → weights
Version all four. Code lives in git. Data lives in DVC (or object storage with hashes). Params and metrics live in an experiment tracker. Weights (the artifact) live in a model registry. Link them together and any model becomes fully reproducible — you can answer "what produced this?" with one lookup.

2. Tracking vs Registry vs Data Versioning

Three related but distinct jobs. Confusing them is the most common beginner mistake.

The three responsibilities

ConceptWhat it capturesAnswers the question
Experiment tracking Every training run: params, metrics, artifacts, code version "Which run scored best, and with what settings?"
Model registry Named, versioned models with stage labels (Staging → Production) "Which model version is live right now?"
Data versioning Snapshots of large datasets tied to git commits "Which exact data trained this model?"
How they fit: Tracking records the experiments. Data versioning pins the inputs. The registry governs the promotion of a chosen model to production. Together they form the lineage.

The full pipeline in one diagram

Data version and code version and params flow into a tracked run, which produces an artifact that gets registered and promoted through stages.

3. MLflow: Tracking & the Model Registry

The most popular open-source tool. It does both experiment tracking and a model registry.

MLflow Tracking

You wrap your training code in an MLflow run and log three kinds of things:

  • Params — inputs you choose (learning rate, epochs, seed)
  • Metrics — outputs you measure (accuracy, loss, F1)
  • Artifacts — files produced (the model, plots, confusion matrix)

Each run also captures the git commit automatically, so code, params, metrics, and the model artifact are stored together.

# illustrative — requires `pip install mlflow`, not runnable here
import mlflow
from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import accuracy_score

mlflow.set_experiment("churn-model")

with mlflow.start_run():
    n_estimators, max_depth = 200, 8

    # 1) log the params you chose
    mlflow.log_param("n_estimators", n_estimators)
    mlflow.log_param("max_depth", max_depth)

    model = RandomForestClassifier(
        n_estimators=n_estimators, max_depth=max_depth, random_state=42
    )
    model.fit(X_train, y_train)

    # 2) log the metric you measured
    acc = accuracy_score(y_test, model.predict(X_test))
    mlflow.log_metric("accuracy", acc)

    # 3) log the model artifact (weights + signature)
    mlflow.sklearn.log_model(model, artifact_path="model")

Run mlflow ui to browse every run, sort by metric, and compare params side by side.

The MLflow Model Registry & stages

Once you pick a good run, you register its model under a name. Each register creates a new numbered version. You then move versions through stages:

None → Staging → Production → Archived

Your serving code always requests "the Production version of churn-model", so promoting a new version is a metadata change — no redeploy needed to switch which weights are live.

# reference — MLflow registry API, illustrative
from mlflow.tracking import MlflowClient

# register the model produced by a run
result = mlflow.register_model(
    model_uri="runs:/<RUN_ID>/model",
    name="churn-model",
)

# promote version 3 to Production after it passes validation
client = MlflowClient()
client.transition_model_version_stage(
    name="churn-model", version=3, stage="Production"
)
Why stages matter: Staging lets you validate a candidate against real traffic shadow tests before it serves users. Production is the single source of truth for "what is live". Archived keeps old versions for instant rollback. See how this plugs into automated pipelines in CI/CD for ML.

4. DVC: Data Version Control

Git handles code, but git chokes on multi-gigabyte datasets. DVC fixes that.

Git-like versioning for large data

DVC stores a tiny pointer file (a .dvc file containing a hash) in git, while the actual large data lives in remote storage (S3, GCS, Azure, SSH). Checking out an old git commit + running dvc checkout restores the exact data snapshot that matched that commit — tying data directly to code history.

# CLI — illustrative, run in a git repo with `pip install dvc`
dvc init                          # set up DVC in the repo
dvc add data/train.csv            # track the dataset; creates data/train.csv.dvc
git add data/train.csv.dvc .gitignore
git commit -m "Track training data v1"

dvc remote add -d storage s3://my-bucket/dvcstore
dvc push                          # upload the actual data to remote storage

# later, on another machine or an old commit:
git checkout <commit>
dvc pull                          # download the exact matching data snapshot
Why it matters: The .dvc pointer travels with your git commit, so a specific code version and a specific data version are locked together. Reproduce any past experiment by checking out the commit and running dvc pull.

How DVC and git split the work

Stored in gitStored in DVC remote
Code, configs, small text files Large datasets, model weights, media
The tiny .dvc pointer files (hash + path) The real bytes, addressed by content hash

5. Weights & Biases (W&B)

A hosted, polished experiment-tracking service — strong on dashboards and collaboration.

Hosted tracking & dashboards

Weights & Biases (wandb) is a SaaS platform for experiment tracking with rich, live dashboards. You add a few lines to your training loop and every run streams params, metrics, system stats (GPU/CPU), and artifacts to a shared web UI — great for teams comparing hundreds of runs and sharing reports.

# illustrative — requires `pip install wandb` and a free account
import wandb

wandb.init(project="churn-model", config={"lr": 0.01, "epochs": 20})

for epoch in range(20):
    # ... training step ...
    wandb.log({"epoch": epoch, "loss": loss, "accuracy": acc})

wandb.finish()
When to reach for W&B: when you want zero-setup hosted dashboards, live training curves, hyperparameter sweeps, and easy team sharing. It also offers Artifacts for model/data versioning and a Model Registry, overlapping with MLflow.

6. Tool Comparison

Which tool versions what?

ToolWhat it versionsBest for
Git Code & small config files The baseline — every project needs it
DVC Large datasets & artifacts (tied to git commits) Reproducible data pipelines, self-hosted storage
MLflow Runs (params/metrics/artifacts) + registered models & stages Open-source, self-hosted tracking + registry in one
W&B Runs, artifacts, models (hosted) Polished hosted dashboards & team collaboration
Common combo: Git for code, DVC for data, and MLflow (or W&B) for experiment tracking + registry. They are complementary, not mutually exclusive — each owns one part of the "version all four" story.

7. Semantic Versioning & Lineage

Version numbers should carry meaning, and every model should trace back to its inputs.

Semantic versioning for models

Borrow MAJOR.MINOR.PATCH from software, adapted to models:

BumpMeaning for a modelExample
MAJOR Breaking change: different input/output schema or architecture 1.4.2 → 2.0.0
MINOR Retrained on new data or improved, same interface 1.4.2 → 1.5.0
PATCH Small fix: bug patch, threshold tweak, no interface change 1.4.2 → 1.4.3
Why it matters: A MAJOR bump warns downstream consumers their code may break (new features expected). A MINOR/PATCH says "safe to upgrade". This lets serving systems and teammates reason about compatibility at a glance.

Lineage: the full paper trail

Lineage is the recorded chain linking a deployed model back to everything that produced it. A well-tracked model version stores references to all four pillars:

  • Code — git commit SHA of the training pipeline
  • Data — DVC hash / dataset version used
  • Params — hyperparameters logged for the run
  • Weights — the registered artifact and its version number
model v1.5.0 → run 8f3a → { commit 9c1e · data d41d · lr=0.01 }
The payoff: When a live model misbehaves, lineage lets you jump from the prediction to the exact code, data, and params in seconds — then reproduce, debug, or roll back with confidence. This is the reproducibility promise from section 1, fully realized. See how the whole lifecycle connects in the ML Workflow.

Quick recap

  • Reproducibility — know which code, data, params & weights made a result
  • Experiment tracking — log params/metrics/artifacts per run (MLflow, W&B)
  • Data versioning — git-like snapshots of big datasets (DVC)
  • Model registry — named, versioned models promoted through stages
  • Lineage + SemVer — trace every model to its inputs, version with meaning
