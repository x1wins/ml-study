🧪 Testing ML Code with PyTest

Catch silent bugs before they wreck your results — test your code, your data, and your model behavior with runnable pytest patterns.

← Back to Learning Path
Big picture: In normal software a bug usually crashes or throws. In ML a bug often stays silent — a wrong tensor shape gets broadcast, a NaN quietly spreads, accuracy drifts — and you only notice when the model is already in production. Tests turn those silent failures into loud, early ones.

1. Why testing ML is different

Traditional tests check code. ML systems have three moving parts that can all break independently.

Three things to test, not one

LayerWhat can silently breakExample test
CodeWrong shape, off-by-one axis, bad normalizationassert out.shape == (batch, classes)
DataNulls, out-of-range values, schema drift, leakageassert df["age"].between(0, 120).all()
Model behaviorAccuracy regression, broken invariants, NaN lossassert acc > 0.8
Why it matters: tests catch silent ML bugs — wrong shapes, NaNs, exploded gradients — that don't crash but quietly ruin results. A model that "runs fine" can still be completely wrong. Assertions make wrongness visible.

The ML test flow

Think of tests as gates the data and model must pass through before you trust an output.

2. PyTest basics

A tiny amount of pytest syntax covers most ML testing needs.

Anatomy of a test

A pytest test is any function whose name starts with test_, containing an assert. If the assertion is false, the test fails.

# file: test_math.py   (runnable)
def add(a, b):
    return a + b

def test_add_basic():
    assert add(2, 3) == 5

def test_add_negative():
    assert add(-1, 1) == 0

Run it from the terminal:

# reference: run all tests, verbose, stop at first failure
pytest -v -x
pytest test_math.py::test_add_basic   # run one specific test

Fixtures — reusable setup

A fixture builds something once (a model, a dataset, a temp file) and hands it to any test that asks for it by name.

# runnable
import numpy as np
import pytest

@pytest.fixture
def eval_batch():
    rng = np.random.default_rng(0)
    X = rng.normal(size=(32, 4))   # 32 samples, 4 features
    y = rng.integers(0, 3, size=32)
    return X, y

def test_batch_shape(eval_batch):
    X, y = eval_batch
    assert X.shape == (32, 4)
    assert y.shape == (32,)

Parametrize — one test, many cases

@pytest.mark.parametrize runs the same test body across many inputs, so each case reports pass/fail independently.

# runnable
import numpy as np
import pytest

def sigmoid(x):
    return 1 / (1 + np.exp(-x))

@pytest.mark.parametrize("x", [-10.0, -1.0, 0.0, 1.0, 10.0])
def test_sigmoid_in_range(x):
    y = sigmoid(x)
    assert 0.0 < y < 1.0            # sigmoid output is strictly between 0 and 1

def test_sigmoid_midpoint():
    assert np.isclose(sigmoid(0.0), 0.5)
Why it matters: parametrize gives you edge-case coverage (very negative, zero, very positive) for free — exactly where numerical bugs like overflow hide.

3. Data & tensor shape tests

The #1 silent ML bug is a shape mismatch that broadcasts instead of erroring.

Assert the exact output shape

Every model output should have a known shape: (batch, classes) for a classifier. Pin it down.

# runnable
import numpy as np

def linear_head(X, W, b):
    # X: (batch, features), W: (features, classes), b: (classes,)
    return X @ W + b

def test_output_shape():
    batch, features, classes = 8, 5, 3
    X = np.zeros((batch, features))
    W = np.zeros((features, classes))
    b = np.zeros(classes)
    out = linear_head(X, W, b)
    assert out.shape == (batch, classes)   # (8, 3)
Why it matters: numpy broadcasting will happily turn a (8, 3) vs (3,) mismatch into a silent wrong result instead of an error. An explicit shape assert is your seatbelt.

Common shape checks

  • assert out.shape == (batch, classes) — classifier logits
  • assert preds.shape == labels.shape — predictions align with targets
  • assert X.ndim == 2 — catch a stray extra dimension early
  • assert len(loader) > 0 — the dataset actually loaded

4. Numerical tests

Floating-point math is never exact — compare with tolerance, and hunt for NaNs.

Compare floats with np.allclose

Never use == on floats. Use np.allclose (or np.isclose) with a tolerance.

# runnable
import numpy as np

def test_allclose_not_equals():
    a = np.array([0.1 + 0.2, 1.0])
    b = np.array([0.3,        1.0])
    assert not np.all(a == b)        # 0.1 + 0.2 != 0.3 exactly
    assert np.allclose(a, b)         # but they are close enough

No NaNs, no infinities, finite gradients

A single NaN poisons an entire tensor. Assert finiteness on outputs and gradients.

# runnable
import numpy as np

def test_outputs_are_finite():
    out = np.array([0.2, 0.8, 0.5])
    assert np.all(np.isfinite(out))          # no NaN, no +/-inf
    assert not np.isnan(out).any()

def test_gradients_finite():
    # a fake gradient tensor from a backward pass
    grad = np.array([[0.01, -0.2], [0.3, 0.05]])
    assert np.isfinite(grad).all()           # exploded/NaN grads would fail here
    assert np.abs(grad).max() < 1e3          # sanity bound: not exploding
Why it matters: a NaN loss won't raise an exception — training just silently stops learning. A finiteness assert in your test suite (and even in training code) catches it at the source.

5. Validation threshold tests

Lock in a minimum quality bar so a regression fails the build, not the customer.

Assert accuracy on a fixed eval set

Pick a small, fixed evaluation set and assert the model clears a threshold. A fixed set makes the test deterministic and repeatable.

# runnable  (uses a trivial rule "model" so it always runs)
import numpy as np

def predict(X):
    # toy model: class 1 if feature-0 is positive, else class 0
    return (X[:, 0] > 0).astype(int)

def accuracy(y_true, y_pred):
    return float(np.mean(y_true == y_pred))

def test_accuracy_above_threshold():
    # fixed eval set: feature-0 sign perfectly determines the label
    X = np.array([[ 1.0, 0.0],
                  [-1.0, 0.0],
                  [ 2.0, 9.0],
                  [-3.0, 1.0],
                  [ 0.5, 2.0]])
    y = np.array([1, 0, 1, 0, 1])
    acc = accuracy(y, predict(X))
    assert acc > 0.8            # here acc == 1.0, comfortably above the bar
Why it matters: a threshold test turns "the model got worse" into a red CI build. Set the bar just below your current, trusted score so real regressions fail fast.

6. Testing data quality

Garbage in, garbage out. Test the data before it ever reaches the model.

Nulls, ranges, and schema

# runnable (pure numpy so it runs anywhere)
import numpy as np

def test_no_nulls():
    ages = np.array([21.0, 34.0, 45.0, 29.0])
    assert not np.isnan(ages).any()         # no missing values

def test_values_in_range():
    ages = np.array([21.0, 34.0, 45.0, 29.0])
    assert (ages >= 0).all() and (ages <= 120).all()

def test_schema_columns():
    # expected column order / names for a fixed dataset
    columns = ["age", "income", "label"]
    expected = ["age", "income", "label"]
    assert columns == expected              # schema drift would fail here
Why it matters: a renamed column or a stray sentinel value like −999 for "missing" can silently skew every prediction. Schema and range checks catch upstream data changes before they train a broken model.

What to check on incoming data

  • No nulls / NaNs in required columns
  • Numeric ranges are physically plausible (age 0 → 120, probability 0 → 1)
  • Categorical values are in the expected set (no unseen labels)
  • Row count and column schema match expectations
  • No duplicate rows between train and eval sets (leakage)

7. Property & invariance tests

Instead of exact outputs, assert properties that must always hold.

Softmax always sums to 1

Softmax turns logits into a probability distribution, so each row must sum to 1 and every value must be in [0, 1].

# runnable
import numpy as np

def softmax(x, axis=-1):
    x = x - np.max(x, axis=axis, keepdims=True)   # numerical stability
    e = np.exp(x)
    return e / e.sum(axis=axis, keepdims=True)

def test_softmax_sums_to_one():
    logits = np.array([[2.0, 1.0, 0.1],
                       [0.5, 0.5, 0.5]])
    probs = softmax(logits, axis=1)
    row_sums = probs.sum(axis=1)
    assert np.allclose(row_sums, 1.0)             # every row is a distribution
    assert (probs >= 0).all() and (probs <= 1).all()

Shuffling inputs must not change accuracy

Accuracy is a set-level metric — reordering the samples (and their matching labels) must give the identical score. If it doesn't, something depends on row order (a bug).

# runnable
import numpy as np

def predict(X):
    return (X[:, 0] > 0).astype(int)

def accuracy(y_true, y_pred):
    return float(np.mean(y_true == y_pred))

def test_shuffle_invariance():
    rng = np.random.default_rng(42)
    X = rng.normal(size=(50, 3))
    y = (X[:, 0] > 0).astype(int)

    acc_original = accuracy(y, predict(X))

    perm = rng.permutation(len(X))       # shuffle rows AND labels together
    acc_shuffled = accuracy(y[perm], predict(X[perm]))

    assert np.isclose(acc_original, acc_shuffled)
Why it matters: invariance tests describe what must be true without pinning an exact number. They survive retraining and catch subtle order-dependence, normalization, and leakage bugs that a single fixed-value assert would miss.

Useful ML invariants to test

InvariantAssertion idea
Softmax is a distributionnp.allclose(probs.sum(axis=1), 1)

8. Where this fits & resources

The testing pyramid for ML

Many fast unit tests (shapes, ranges, invariants) at the base; fewer, slower behavior and threshold tests near the top.

Practical order: write the cheap unit tests first (shapes, NaNs, softmax sums to 1). They run in milliseconds and catch the majority of silent bugs. Save the slow train-and-evaluate threshold tests for CI.
