🔄 CI/CD for ML: Automated Pipelines

From push to production — how continuous integration, delivery, and training keep ML code, data, and models shippable without the manual toil.

1. What is CI/CD? (and how ML differs)

Two ideas that automate the path from a code change to a running product.

The two (or three) letters

  • CI — Continuous Integration: every push is automatically built, linted, and tested, so broken code is caught in minutes instead of days.
  • CD — Continuous Delivery/Deployment: once checks pass, the change is automatically packaged and (optionally) released to production.
  • CT — Continuous Training: the ML-specific extra — pipelines that retrain and re-evaluate models when data or code changes.
Why it matters: small changes checked often means small bugs found early. The alternative — a big scary "integration day" — is where projects go to break.

How ML CI/CD differs from normal software

In plain software you version and test code. In ML you also version and validate data and models — three moving parts instead of one.

AspectNormal software CI/CDML CI/CD (+ CT)
What you shipCodeCode · data · trained model
TestsUnit · integration+ data checks, model metrics, drift
Build outputBinary / container+ model artifact in a registry
TriggerCode push / PR+ new data, schedule, metric decay
"Passing" meansTests greenTests green and metrics above threshold
Key gotcha: code can be correct while the model is still bad. A green test suite does not guarantee good accuracy — you also gate on metrics. See Testing ML Code for the testing side.

2. GitHub Actions basics

The most common way to run CI/CD right where your code lives.

The vocabulary

  • Workflow — a YAML file in .github/workflows/ describing what to run automatically.
  • Trigger (on:) — the event that starts a workflow, e.g. push, pull_request, schedule, or manual workflow_dispatch.
  • Job — a group of steps that run together on one machine. Jobs can run in parallel or depend on each other with needs:.
  • Step — a single command or reusable action inside a job.
  • Runner — the machine that executes a job (GitHub-hosted like ubuntu-latest, or self-hosted, e.g. a GPU box for training).
Mental model: an event triggers a workflow, which contains jobs, which contain steps, which run on a runner.

3. A starter workflow (lint, format, test)

A short, real workflow that runs on every push: check out code, set up Python, install deps, lint with ruff, verify formatting with black, then run pytest.

.github/workflows/ci.yml (illustrative — runs on GitHub Actions)

name: CI

on:
  push:
    branches: [ main ]
  pull_request:

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt
          pip install ruff black pytest

      - name: Lint (ruff)
        run: ruff check .

      - name: Format check (black)
        run: black --check .

      - name: Run tests (pytest)
        run: pytest -q
Read it top-down: on: says when, jobs: says what. Each - name: is one step. uses: pulls a prebuilt action; run: executes a shell command on the runner.

The flow at a glance

A push kicks off CI. Lint and test guard the code; train/eval produces metrics; a gate blocks deploy unless everything is green.

4. Formatting & linting: black and ruff

Two fast tools that keep a team's Python consistent and catch mistakes early.

What each one does

ToolJobTypical command
black Auto-formatter — rewrites code to one consistent style (spacing, quotes, line length) black . · black --check .
ruff Linter (and formatter) — flags bugs, unused imports, and style issues, very fast ruff check . · ruff check --fix .

Format = how code looks (whitespace, layout). Lint = whether code is likely wrong or smelly (unused variable, undefined name). In CI you usually run black in --check mode so it fails the build instead of editing files.

# local: fix everything before pushing
ruff check --fix .
black .

# CI: fail if anything is off (illustrative)
ruff check .
black --check .
Why it matters in teams: when a formatter owns style, code reviews stop arguing about spaces and quotes and focus on logic. Diffs shrink, and "it works on my machine" style drift disappears. Automate the boring checks so humans review the important stuff.

5. Continuous training & automated evaluation

The ML twist: pipelines that retrain and re-score models, not just test code.

What can trigger retraining?

  • New data — a fresh labeled batch lands in your data store.
  • Schedule — nightly or weekly retrain (on: schedule with cron).
  • Metric decay / drift — monitoring flags accuracy dropping in production.
  • Code change — a new feature or model architecture is merged.
# scheduled retrain trigger (illustrative)
on:
  schedule:
    - cron: "0 3 * * 1"   # every Monday 03:00 UTC
  workflow_dispatch: {}    # allow manual runs too
Automated evaluation is the point: retraining is only useful if the pipeline also scores the new model and compares it to the current one. Never auto-ship a model just because it trained — ship it because it's better.

A tiny evaluation gate in code (reference — runs in your train job)

import json, sys

THRESHOLD = 0.85          # minimum acceptable accuracy

metrics = json.load(open("metrics.json"))
acc = metrics["accuracy"]

print(f"candidate accuracy = {acc:.3f} (threshold {THRESHOLD})")

if acc < THRESHOLD:
    print("Gate FAILED: model below threshold, blocking deploy")
    sys.exit(1)            # non-zero exit fails the CI step

print("Gate PASSED: model eligible for registration")

A non-zero exit stops the pipeline, so a weak model never reaches deploy. Registering the passing model is covered in model-registry.html.

6. Model & data validation gates

Automatic checks that must pass before a model is allowed to ship.

What to gate on before deploy

GateChecksBlocks deploy if…
Data validationSchema, ranges, nulls, class balanceInput data is malformed or drifted
Model metricsAccuracy, F1, AUC on a holdout setScore is below threshold
Regression checkNew model vs. current production modelNew model is worse than the old one
Fairness / slicesMetrics across key subgroupsA subgroup degrades badly
Artifact integrityModel loads, expected input/output shapeArtifact is broken or wrong shape
Why gates matter: a gate is the last automated line of defense. It converts "we hope the model is good" into "the pipeline proved the model is good, or it didn't deploy." Only after gates pass do you register the model and hand it to serving — see model-serving.html.

7. A typical ML CI/CD pipeline

The stages most production ML teams converge on, in order.

Stages, start to finish

lint → test → train/eval → register → deploy
StageWhat happensFails the build when…
1. Lintruff + black check code style & obvious bugsStyle or lint errors
2. Testpytest runs unit & data testsAny test fails
3. Train/evalTrain candidate model, compute metricsMetrics below threshold (the gate)
4. RegisterSave the passing model + metadata to a registryArtifact can't be stored/validated
5. DeployRoll the registered model out to servingHealth check / smoke test fails
Order is deliberate: cheap, fast checks (lint, test) run first so you fail in seconds, not after an expensive training run. Training happens only once the code is known good.

Cross-links for the later stages: Testing ML Code (stages 1–2), model-registry.html (stage 4), and model-serving.html (stage 5).

Quick recap

  • CI — auto-build/lint/test every change
  • CD — auto-package and release when checks pass
  • CT — retrain & re-evaluate models on new data or a schedule
  • Gates — block deploy unless metrics and data checks pass
  • Pipeline — lint → test → train/eval → register → deploy
