🌐 Distributed Training: Data, Tensor & Pipeline Parallelism

When a model or dataset won't fit on one GPU, you split the work across many. Here's how — data, tensor, and pipeline parallelism — and how to pick the right one.

← Back to Learning Path
Big picture: There are only two things you can split across GPUs — the data (the batch) or the model (the weights and the math). Every distributed strategy is a combination of those two ideas. Figure out your bottleneck first, then pick.

1. Why Distribute at All?

Two walls force you off a single GPU: the model doesn't fit, or training would take forever.

Two hard limits of one GPU

  • Memory wall — a 70B-parameter model in fp16 needs ~140 GB just for the weights. No single GPU (even an 80 GB H100) holds that, let alone gradients and optimizer state.
  • Time wall — even if the model fits, one GPU chewing through a trillion-token dataset could take months. More GPUs process more data in parallel.
Why it matters: The strategy you choose depends on which wall you hit. Too-slow-but-fits → split the data. Won't-fit → split the model. Both → combine them.

The core question

bottleneck = batch throughput  OR  model size → fits in memory?

Keep this question in mind through every section — it's the whole decision tree.

2. Data Parallelism (the most common)

Replicate the whole model on every GPU, split the batch, average the gradients. Simple and effective.

The idea

Each GPU holds an identical copy of the model. You split the mini-batch into chunks — one per GPU. Each GPU does a forward and backward pass on its chunk and produces its own gradients. Then all GPUs all-reduce (sum then divide) their gradients so everyone ends the step with the same averaged gradient and stays in sync.

Why average, not sum? Averaging keeps the gradient at the same scale as a single big batch. It's mathematically equivalent to training on the combined batch on one giant GPU — you just get there faster with N GPUs.

The gradient-averaging idea

If GPU i computes gradient gi on its slice, the synced gradient every GPU uses is:

ḡ = (g0 + g1 + … + gN−1) ÷ N

This is exactly what an all-reduce does: it sums a value across all GPUs and hands the result back to every one of them, so all model copies apply the identical update and never drift apart.

# PyTorch DistributedDataParallel (DDP) — reference sketch (needs a multi-GPU launch)
import torch
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

dist.init_process_group(backend="nccl")          # NCCL = NVIDIA GPU comms
model = MyModel().cuda()
model = DDP(model)                                # wraps model; hooks all-reduce into backward()

for x, y in loader:                               # each rank sees a different shard of data
    loss = loss_fn(model(x.cuda()), y.cuda())
    loss.backward()                               # DDP averages gradients across ranks here
    optimizer.step()
    optimizer.zero_grad()

Launch with torchrun --nproc_per_node=8 train.py. Illustrative: it won't run in a single-process notebook without a real multi-GPU setup.

3. The Memory Problem

Data parallelism is great for speed — but it replicates everything. That's wasteful, and it doesn't help if the model won't fit.

What actually eats your GPU memory

Training memory is not just the weights. For every parameter you also store gradients and optimizer state (Adam keeps two extra values — momentum and variance):

ItemBytes per parameter (mixed precision, Adam)
Parameters (fp16)2
Gradients (fp16)2
Optimizer — fp32 master weights4
Optimizer — Adam momentum (fp32)4
Optimizer — Adam variance (fp32)4
Total≈ 16 bytes / parameter
1B params × 16 bytes ≈ 16 GB  (before activations!)
Why it matters: Plain data parallelism stores those 16 bytes/param on every GPU. Eight GPUs = eight identical copies of the optimizer state. That's the waste ZeRO and FSDP fix.

4. ZeRO & FSDP — Shard the State

Instead of every GPU holding a full copy of the optimizer state, split it up so each GPU owns only a slice.

The intuition

Data parallelism duplicates params, gradients, and optimizer state on all N GPUs. ZeRO (“Zero Redundancy Optimizer”, from DeepSpeed) asks: why keep N copies? Split that state so each GPU stores only 1/N of it, and gather the missing pieces on demand during the step. You trade a little extra communication for a huge memory saving.

StageWhat it shards across GPUsMemory saved
ZeRO-1Optimizer states~4× on optimizer state
ZeRO-2Optimizer states + gradientsMore (gradients too)
ZeRO-3Optimizer states + gradients + parametersLargest — scales with N
PyTorch FSDP (Fully Sharded Data Parallel) is essentially ZeRO-3 built into PyTorch: it shards params, gradients, and optimizer state, then all-gathers each layer's weights only for the moment it's needed in forward/backward, and frees them right after.

ZeRO-3 / FSDP mental model

  • Each GPU permanently owns only its 1/N shard of every layer's weights.
  • Just before a layer runs, GPUs all-gather the full weights for that layer.
  • After the layer finishes, the gathered copy is freed — memory reused.
  • Gradients are reduce-scattered so each GPU keeps only its shard's gradient.
# PyTorch FSDP — reference sketch (needs multi-GPU launch)
import torch
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP

model = MyBigModel().cuda()
model = FSDP(model)          # params/grads/optimizer state sharded across ranks
# training loop is the same as DDP; FSDP handles gather/free/scatter under the hood

Still data parallel (each GPU sees different data), but the model state is sharded — so you can train models far larger than one GPU could hold.

5. Tensor Parallelism (Megatron style)

Split a single big matrix multiply across GPUs. One layer becomes a team effort.

The idea

Some layers are so large that even one layer's weight matrix won't fit, or one matmul is too slow. Tensor parallelism splits an individual operation — e.g. a matrix multiply Y = X W — by cutting the weight matrix W into column blocks. Each GPU multiplies X by its block, producing part of the output; the pieces are then concatenated or summed.

W = [ WA | WB ] ⇒ Y = [ X·WA | X·WB ]

This is the Megatron-LM approach: it splits the attention and MLP matmuls of a Transformer block across GPUs. See Transformers for what those blocks are.

Cost: tensor parallelism needs an all-reduce inside every layer (twice per Transformer block). That's heavy, chatty communication — so it's normally kept within a single node where GPUs share fast NVLink, never across slow network links.

6. Pipeline Parallelism

Cut the model into consecutive stages, one stage per GPU, and stream micro-batches through like an assembly line.

The idea

Put layers 1–10 on GPU 0, layers 11–20 on GPU 1, and so on. Data flows through the stages in order. The problem: if GPU 0 does layer 1 then waits for the whole rest of the network to finish before it can start the next batch, most GPUs sit idle. The fix is to split each batch into small micro-batches and keep the pipeline full, like an assembly line.

The bubble: at the start (filling the pipeline) and end (draining it) some GPUs have nothing to do. That idle time is the pipeline bubble. More micro-batches → smaller bubble as a fraction of total time → better GPU utilization.

7. Combining Them (3D Parallelism)

Frontier-scale training uses all three at once. Each solves a different problem, so they stack.

Three axes, one job

  • Tensor parallel — within a node (fast NVLink), split each layer's matmuls.
  • Pipeline parallel — across nodes, split the layers into stages.
  • Data parallel (often ZeRO/FSDP) — replicate the whole pipeline to chew through more data.
total GPUs = data-parallel × pipeline-stages × tensor-parallel

Example: 8-way tensor × 4-stage pipeline × 16-way data = 512 GPUs training one model. This layout is how models like GPT-scale and LLaMA-scale networks are trained.

Ordering rule of thumb: put the chattiest parallelism (tensor) on the fastest links (inside a node), the less chatty one (pipeline) across nodes, and data parallel on the outside. Match communication volume to available bandwidth.

8. Communication Cost & Hardware

Every split adds communication. The interconnect between GPUs often decides whether a strategy is fast or a bottleneck.

The operations that move data

CollectiveWhat it doesShows up in
all-reduceSum a tensor across all GPUs, give result back to allData parallel (gradients), tensor parallel
all-gatherEach GPU collects everyone's shard to rebuild the full tensorZeRO-3 / FSDP (weights)
reduce-scatterSum, then hand each GPU only its slice of the resultZeRO / FSDP (gradients)
point-to-pointSend activations to the next stagePipeline parallel
Why it matters: All-reduce volume scales with model size. If your GPUs talk over a slow link, communication can dominate and your expensive GPUs sit waiting. This is why the interconnect matters as much as raw compute — see Hardware Acceleration.

Bandwidth tiers (fast → slow)

  • NVLink / NVSwitch — GPU-to-GPU inside a node, hundreds of GB/s. Best for tensor parallelism.
  • PCIe — GPU-to-host / older interconnect, much slower than NVLink.
  • InfiniBand / RoCE — node-to-node network. Good for pipeline & data parallel across machines.
  • Ethernet — slowest common option; fine for loosely-coupled data parallel, painful for tensor parallel.
rule: chatty strategy → fast link · match traffic to bandwidth

9. Comparison & How to Choose

Strategy comparison

StrategyWhat it splitsWhen to use
Data Parallel (DDP) The batch (model replicated) Model fits on one GPU; you just want to go faster. The default first step.
ZeRO / FSDP Optimizer state, gradients, params (sharded) Data parallel, but the model + optimizer state won't fit. Biggest memory win.
Tensor Parallel Individual layers / matmuls A single layer is too big or too slow. Keep it within a node (NVLink).
Pipeline Parallel Groups of layers into stages Model has many layers and spans multiple nodes. Watch the bubble.
3D (combined) All of the above Frontier-scale models on hundreds/thousands of GPUs.
How to choose — match the split to your bottleneck: If your model fits and you only want throughput, use data parallelism (split the batch). If your model doesn't fit, start with ZeRO/FSDP; if a single layer is still too big, add tensor parallelism; if the layer count is the issue, add pipeline parallelism. Batch bottleneck → split data. Model-size bottleneck → split model. Reach for combinations only when one axis isn't enough.

A quick decision sketch

# reference decision tree (pseudocode, not runnable)
if model_fits_on_one_gpu:
    use "DDP"                         # split the batch, all-reduce grads
elif model_plus_optimizer_too_big:
    use "ZeRO-3 / FSDP"               # shard params + grads + optimizer state
    if single_layer_still_too_big:
        add "tensor parallel"         # split matmuls, keep on NVLink
    if too_many_layers_for_one_node:
        add "pipeline parallel"       # stage layers, use micro-batches
# very large scale -> combine all three (3D parallelism)
