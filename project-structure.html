From notebook chaos to a maintainable, reproducible repo — a practical layout your team (and future you) can actually work with.

1. Why structure matters

The most common ML failure mode isn't a bad model — it's a project nobody else can run.

From notebook chaos to a real repo

Every ML project starts as a single notebook: load data, hack a model, print accuracy. That's fine for exploration. But the moment you need to retrain, hand it off, or deploy it, an untracked notebook full of hard-coded paths and out-of-order cells becomes a liability.

A structured repo turns "it worked on my machine last Tuesday" into "clone, install, run" — every time, for everyone.

Notebook chaosMaintainable repo
Cells run out of orderDeterministic scripts & entry points
Hard-coded paths & magic numbersConfig files (yaml)
Copy-pasted code across notebooksReusable modules in src/
No tests — "looks right"Unit tests in tests/
Unpinned deps → breaks laterPinned requirements.txt
If it only works in your notebook, it doesn't work. Reproducibility is a feature, not a chore. A model you can't rerun is a screenshot.

2. The recommended layout

A sensible default that scales from solo experiments to a team codebase.

Directory tree

my-ml-project/
├─ data/                  # not tracked in git (see .gitignore)
│  ├─ raw/                # original, immutable source data
│  └─ processed/          # cleaned / feature-engineered data
├─ notebooks/             # exploration only (not the source of truth)
│  └─ 01_explore.ipynb
├─ src/                   # the actual, importable package
│  ├─ __init__.py
│  ├─ data/               # loading & preprocessing
│  │  └─ dataset.py
│  ├─ models/             # model definitions
│  │  └─ net.py
│  ├─ train.py            # training entry point
│  └─ inference.py        # prediction / serving entry point
├─ configs/               # experiment settings (yaml)
│  └─ baseline.yaml
├─ tests/                 # unit & integration tests
│  └─ test_dataset.py
├─ requirements.txt       # pinned dependencies
├─ pyproject.toml         # packaging & tool config
├─ README.md              # what it is, how to run it
├─ .gitignore             # excludes data/, checkpoints, secrets
└─ Dockerfile             # reproducible runtime environment

Reference layout — adjust names to your framework, but keep the four pillars: data, src, configs, tests.

3. Folder-by-folder reference

What lives where, and why

Folder / filePurpose
data/raw/Original, immutable source data. Never edited by code. Git-ignored.
data/processed/Cleaned, feature-engineered data produced by src/. Regenerable, so git-ignored.
notebooks/Exploration and reporting only. Prototype here, then promote stable code into src/.
src/data/Dataset loading and preprocessing logic (importable, testable).
src/models/Model architecture definitions, decoupled from training.
src/train.pyTraining entry point: reads a config, builds a model, fits, saves checkpoints.
src/inference.pyPrediction / serving entry point: loads a trained model and produces outputs.
configs/YAML files describing an experiment (paths, hyperparameters, seed). No values hard-coded in code.
tests/Unit & integration tests for the code in src/. Your safety net for refactors.
requirements.txtPinned dependency versions so environments are reproducible.
pyproject.tomlPackaging metadata & tool config (build, linters, formatters).
README.mdWhat the project is, how to install, and how to run it.
.gitignoreExcludes data/, checkpoints, caches, and secrets from version control.
DockerfileDefines a reproducible runtime image for training and serving.

4. Separation of concerns

Three things change for different reasons — keep them apart: config, code, and data.

The three layers

  • Config — what to run: which dataset, which hyperparameters, which seed. Changes often.
  • Code — how to run it: the logic in src/. Changes when behavior changes.
  • Data — what it runs on: large, external, versioned separately. Never committed to git.
Why it matters: when a hyperparameter is buried in a code cell, every experiment is a code edit (and a chance to break something). When it lives in a config file, you change one line, keep a record, and never touch the tested code.

A minimal .gitignore

# reference .gitignore for an ML project
data/                 # raw + processed data live outside git
*.ckpt                # model checkpoints
*.pth
__pycache__/
.env                  # secrets & credentials — never commit
.ipynb_checkpoints/
.venv/

Track code and configs; keep data, checkpoints, and secrets out.

5. Config-driven experiments

One config file = one reproducible experiment. Change the file, not the code.

A YAML experiment config

# configs/baseline.yaml  (reference)
seed: 42
data:
  path: data/processed/train.csv
  batch_size: 64
model:
  hidden_units: 128
  dropout: 0.2
train:
  epochs: 20
  learning_rate: 0.001
  optimizer: adam

To try a new idea, copy this file to configs/bigger.yaml, bump hidden_units, and rerun. Both configs stay in git as a permanent record.

Wiring config into code with argparse

The simplest approach: pass a config path on the command line, load the YAML, and use it. For larger projects, Hydra adds config composition, overrides, and sweeps — but the idea is the same: keep settings out of code.

# src/train.py  (illustrative — requires pyyaml + your own model code)
import argparse
import yaml

def load_config(path):
    with open(path) as f:
        return yaml.safe_load(f)

def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--config", default="configs/baseline.yaml")
    args = parser.parse_args()

    cfg = load_config(args.config)
    print("seed        :", cfg["seed"])
    print("batch_size  :", cfg["data"]["batch_size"])
    print("epochs      :", cfg["train"]["epochs"])
    # build model / dataset from cfg, then train ...

if __name__ == "__main__":
    main()
# run different experiments without editing code (reference CLI)
python -m src.train --config configs/baseline.yaml
python -m src.train --config configs/bigger.yaml
Hydra idea: instead of one file, compose configs (data + model + train) and override on the command line, e.g. python -m src.train train.learning_rate=0.01. Great for hyperparameter sweeps.

6. Packaging your project

Make src/ a real, importable package so imports work from anywhere.

Editable install with pyproject.toml

A pyproject.toml declares your project as an installable package. Installing it in editable mode (pip install -e .) means import src... works from any directory, and your edits take effect immediately — no sys.path hacks.

# pyproject.toml  (reference)
[build-system]
requires = ["setuptools>=61"]
build-backend = "setuptools.build_meta"

[project]
name = "my-ml-project"
version = "0.1.0"
requires-python = ">=3.10"
dependencies = [
  "numpy==1.26.4",
  "pyyaml==6.0.1",
]

[tool.setuptools.packages.find]
where = ["."]
# install once, then import from anywhere (reference CLI)
pip install -e .
python -c "import src; print('package importable')"
Why -e (editable)? Without it you'd reinstall after every code change. With it, the installed package points at your working tree, so src/ is always up to date while staying a proper, importable module.

7. Reproducibility

Same code + same data + same seed + same deps = same result. Every time.

Pin your dependencies

Unpinned dependencies are a time bomb: a library releases a new version, and your code silently breaks or your metrics shift. Pin exact versions so the environment is identical months later.

# requirements.txt  (reference — note the exact == pins)
numpy==1.26.4
pandas==2.2.2
scikit-learn==1.5.1
pyyaml==6.0.1
# capture the versions you actually used (reference CLI)
pip freeze > requirements.txt

Set every random seed

ML is full of randomness: data shuffling, weight initialization, dropout. Seed all of it so a run is repeatable.

import os
import random
import numpy as np

def set_seed(seed=42):
    os.environ["PYTHONHASHSEED"] = str(seed)
    random.seed(seed)
    np.random.seed(seed)
    # torch.manual_seed(seed)              # if using PyTorch
    # torch.cuda.manual_seed_all(seed)     # for GPU runs

set_seed(42)

# proof it's deterministic: same seed -> same numbers
a = np.random.rand(3)
set_seed(42)
b = np.random.rand(3)
print("reproducible:", np.allclose(a, b))   # True
Reproducibility checklist: pinned deps, a fixed seed, config in git, data versioned outside git, and a Dockerfile so the runtime itself is fixed. Miss one and "it worked before" becomes a debugging session.
