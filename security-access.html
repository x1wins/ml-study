🔑 Access Control & Auditing

Who is allowed to call your model, what are they allowed to do, and how do you prove what happened — authentication, authorization, zero trust, and tamper-evident logs.

← Back to Learning Path
Big picture: An LLM endpoint is expensive and powerful, so it is a target. Access control answers three questions: who are you? (authentication), what may you do? (authorization), and can we prove it later? (auditing). Get these right and most of your attack surface disappears.

1. Securing Model / LLM API Endpoints

Your inference endpoint is a public door into an expensive, capable system. Lock it before you ship.

What makes a model endpoint different

Unlike a typical CRUD API, a model endpoint has three unusual risks: each call can be expensive (GPU time, token cost), the input is free-form text (hard to validate, easy to abuse → see the adversarial page), and the output can leak training data or system prompts. So the front door needs identity, permission, quotas, and logging — all four.

  • Terminate TLS — every request over HTTPS, never plain HTTP
  • Put a gateway in front — the model process should never be directly reachable
  • Authenticate every request — no anonymous access to inference
  • Authorize per action — who can call which model / which route
  • Meter usage — rate limits and quotas per caller
  • Log the who/what/when — for billing, abuse detection, and forensics
Why it matters: A leaked, unauthenticated inference URL can be scraped and drained — running up a huge bill or exfiltrating data — in minutes. The gateway is where you enforce all of this in one place. See Model Serving for how that gateway fits the serving stack.

2. Authentication vs Authorization · Keys vs OAuth/JWT

Two different questions people constantly confuse. Get the vocabulary straight first.

AuthN ≠ AuthZ

 Authentication (AuthN)Authorization (AuthZ)
QuestionWho are you?What are you allowed to do?
ProvesIdentityPermission
ExampleValid API key / signed JWTThis key may call gpt-small but not gpt-large
Fails with401 Unauthorized403 Forbidden
Why it matters: Authenticating a caller does not mean they may do anything. A valid token that is allowed to call every model is a common, dangerous mistake. Always pair identity (AuthN) with a per-action permission check (AuthZ).

API keys vs OAuth / JWT

MechanismHow it worksGood forWatch out
API key Long random secret sent in a header Server-to-server, simple integrations Long-lived; if leaked it works until revoked
OAuth 2.0 Delegated authorization flow issues short-lived tokens User-facing apps, third-party access More moving parts; needs an auth server
JWT Signed token carrying claims (who, scopes, expiry) Stateless verification at the gateway Cannot be revoked before expiry → keep TTL short

A JWT is a signed, self-describing token. The gateway verifies the signature and reads the claims — no database lookup needed. Below is a reference of a decoded JWT payload (illustrative):

// JWT payload (decoded) — reference only
{
  "sub": "svc-chatbot-prod",     // who (subject / identity)
  "scope": ["model:gpt-small:invoke"],  // what they may do
  "iat": 1732600000,             // issued at
  "exp": 1732603600,             // expires (short TTL → 1 hour)
  "iss": "https://auth.example.com"
}
Rule of thumb: API keys for machine clients you control; OAuth/JWT when users or third parties are involved. Either way — short-lived, scoped, and revocable.

Verifying a bearer token at the gateway (illustrative)

# illustrative FastAPI dependency — not runnable here (needs PyJWT + secrets)
from fastapi import Header, HTTPException
import jwt  # PyJWT

PUBLIC_KEY = "..."  # loaded from a vault, never hardcoded

def require_scope(needed: str):
    def checker(authorization: str = Header(...)):
        if not authorization.startswith("Bearer "):
            raise HTTPException(401, "missing bearer token")   # AuthN failure
        token = authorization.split(" ", 1)[1]
        try:
            claims = jwt.decode(token, PUBLIC_KEY, algorithms=["RS256"])
        except jwt.PyJWTError:
            raise HTTPException(401, "invalid token")           # AuthN failure
        if needed not in claims.get("scope", []):
            raise HTTPException(403, "insufficient scope")      # AuthZ failure
        return claims
    return checker

Notice the two distinct failure modes: 401 when identity cannot be proven, 403 when identity is fine but permission is missing.

3. Rate Limiting & Input Size Limits

Even authenticated callers must be metered. Limits protect cost, availability, and the model itself.

Rate limiting

Cap how many requests (or tokens) a caller may use per window. A common approach is the token bucket: each caller has a bucket that refills at a fixed rate; a request costs tokens; an empty bucket returns 429 Too Many Requests.

allowed if bucket ≥ cost  ·  refill = rate × Δt
import time

class TokenBucket:
    def __init__(self, capacity, refill_per_sec):
        self.capacity = capacity
        self.tokens = capacity
        self.rate = refill_per_sec
        self.last = time.monotonic()

    def allow(self, cost=1):
        now = time.monotonic()
        # refill based on elapsed time
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= cost:
            self.tokens -= cost
            return True
        return False

bucket = TokenBucket(capacity=5, refill_per_sec=1)
print([bucket.allow() for _ in range(7)])
# [True, True, True, True, True, False, False]  (first 5 pass, rest throttled)

This snippet is runnable and shows the burst of 5 then throttling.

Input size limits

Reject oversized inputs before they reach the model. Unbounded input is both a cost risk (huge context = huge bill) and an abuse vector (prompt-stuffing, denial of service).

  • Set a max request body size at the gateway (e.g. reject > 256 KB)
  • Cap prompt token count before inference (count, then reject or truncate)
  • Bound the number of items in batch requests
  • Cap max_tokens on the output so a single call cannot run away
Why it matters: Limits turn "one caller can hurt everyone" into "one caller hurts only their own quota." They are the cheapest availability control you have.

4. The Principle of Least Privilege

Give every identity the minimum access it needs to do its job — nothing more.

What least privilege means in practice

A service that only needs to invoke one small model should not have a token that can invoke every model, read the training data, or deploy new versions. Scope each credential tightly and grant permissions per action, not per system.

  • Scoped tokens — model:gpt-small:invoke, not admin:*
  • Separate identities — the chatbot service ≠ the fine-tuning job ≠ a human operator
  • Read vs write split — inference callers cannot modify or delete models
  • Time-boxed access — short token TTLs; expire unused grants
  • Deny by default — nothing is allowed unless a policy explicitly permits it
Why it matters: Least privilege shrinks the blast radius. If one credential leaks, the attacker gets exactly one narrow capability — not the keys to the kingdom. It pairs directly with zero trust below.

5. Zero Trust Architecture: PEP & PDP

"Never trust, always verify." No request is trusted just because it is on the internal network.

The core idea

Old model: a hard perimeter (firewall), everything inside trusted. Zero trust drops that assumption — every request is authenticated and authorized, every time, regardless of where it comes from. Trust is never inherited from network location; it is earned per request by presenting a valid token that a policy engine checks.

PEP and PDP — the two roles

ComponentFull nameJob
PEP Policy Enforcement Point Sits in the request path (the gateway). Intercepts each call, asks the PDP for a decision, then enforces it — allow through or block.
PDP Policy Decision Point The brain. Evaluates the token, the requested action, and the policy rules, then returns a decision: permit or deny.

How a request is checked, step by step (never trust, always verify):

  1. Client sends a request with a bearer token to the PEP (gateway).
  2. PEP extracts the token and the requested action and asks the PDP: "may this subject do this?"
  3. PDP verifies the token signature & expiry, checks scopes against policy, returns permit or deny.
  4. PEP enforces: on permit it forwards to the model API; on deny it returns 401/403.
  5. Every decision is written to the audit log — allowed or denied.
Why it matters: Separating decision (PDP) from enforcement (PEP) means policy lives in one place and every gateway enforces it consistently. Change a rule once → every entry point obeys it. This is the backbone of zero trust.

6. Auditing & Logging

If you cannot answer "who did what, when?", you cannot detect abuse, debug incidents, or bill accurately.

Log the who / what / when

Every request that hits the gateway should produce a structured audit record. At minimum:

  • Who — subject/identity from the token (not the raw token)
  • What — action, model name, route, decision (permit/deny)
  • When — timestamp, request id, source IP
  • Outcome — status code, latency, tokens used / cost
// structured audit record — reference (JSON lines)
{
  "ts": "2026-09-27T18:54:05Z",
  "request_id": "req_9f2a...",
  "subject": "svc-chatbot-prod",     // who
  "action": "model:gpt-small:invoke",// what
  "decision": "permit",
  "status": 200,
  "input_tokens": 812,
  "output_tokens": 240,
  "src_ip": "10.4.2.19"
}

Prompt & response logging for abuse detection

Logging prompts and responses lets you detect jailbreak attempts, prompt injection, and misuse patterns (tie this to the Adversarial & Robustness page). But this data is sensitive, so handle it carefully:

  • Store prompt/response logs separately from the low-sensitivity audit trail
  • Redact or hash PII before storage — see the Privacy & Data Protection page
  • Apply short retention windows and strict access controls to this store
  • Sample rather than log everything when volume is high

Tamper-evident logs

An attacker who breaks in will try to erase their tracks. Tamper-evident logs make changes detectable: each entry includes a hash of the previous entry, forming a chain. Alter one record and every hash after it breaks — the tampering is obvious.

hn = hash( entryn · hn−1 )
import hashlib, json

def chain(entries):
    prev = "GENESIS"
    out = []
    for e in entries:
        payload = json.dumps(e, sort_keys=True) + prev
        h = hashlib.sha256(payload.encode()).hexdigest()
        out.append({**e, "prev": prev, "hash": h})
        prev = h
    return out

log = chain([{"who": "alice", "act": "invoke"},
             {"who": "bob",   "act": "deploy"}])
for row in log:
    print(row["who"], row["hash"][:12])
# tampering with any earlier entry changes all later hashes

This snippet is runnable. For production, also ship logs off-host to append-only / WORM storage so a compromised host cannot rewrite history.

Never log secrets or PII. No API keys, tokens, passwords, or raw personal data in logs. Log the subject id, not the token; a hash of an email, not the email. Logs are widely readable — treat them as if they will leak.

7. Secrets Management

Keys, tokens, and connection strings are the crown jewels. Where you put them decides whether they leak.

Never hardcode keys

A hardcoded key committed to git is effectively public — forever, even after you delete it, because git history remembers. Load secrets at runtime from the environment or a vault.

# reference — loading secrets the right way
import os

# GOOD: from environment (injected by the platform, never committed)
api_key = os.environ["MODEL_API_KEY"]

# BAD (do NOT do this):
# api_key = "sk-live-abc123..."   # hardcoded → leaks into git history
ApproachWhen to useNotes
Environment variablesSimple deployments, containersInjected by the platform; keep out of images & logs
Secrets vaultProduction, many servicesCentral store, access-controlled, audited, supports rotation
Managed identityCloud services calling cloud servicesNo long-lived secret at all — short-lived tokens minted on demand
  • Rotate secrets regularly and immediately on suspected leak
  • Give each service its own secret (least privilege → easy, targeted revocation)
  • Add a .gitignore for .env files; scan commits for secrets in CI
  • Grant vault read access per identity, and audit every secret fetch
Why it matters: Most real-world breaches start with a leaked credential, not a clever exploit. A vault + rotation + least privilege turns a leaked key from a catastrophe into a quick, contained revoke.

8. Controls Cheat Sheet

Control → purpose

ControlPurpose
TLS / HTTPSEncrypt data in transit so tokens and prompts can't be sniffed
Authentication (keys / JWT)Prove who is calling — no anonymous inference
Authorization (scopes / policy)Enforce what each identity may do (per model, per action)
Least privilegeShrink the blast radius if a credential leaks
Rate limitingProtect cost & availability; isolate abusive callers
Input size limitsBlock cost blowups and prompt-stuffing / DoS
PEP (enforcement)Consistently allow/deny every request at the gateway
PDP (decision)Centralize policy so rules change in one place
Audit loggingAnswer who/what/when for billing, forensics, compliance
Prompt/response loggingDetect abuse & jailbreaks (redact PII first)
Tamper-evident logsMake log alteration detectable via hash chaining
Secrets vault + rotationKeep keys out of code; contain leaks fast
Defense in depth: No single control is enough. Layer them — TLS, then AuthN, then AuthZ, then rate limits, then logging — so that if one layer fails, the next still stands. An attacker who slips past authentication still faces least-privilege scopes, quotas, and a tamper-evident record of everything they touched. Assume any one control will eventually fail, and design so that failure is not catastrophic.

Quick recap

  • AuthN — proves identity (401 on failure)
  • AuthZ — proves permission (403 on failure)
  • Least privilege — minimum access, deny by default
  • Zero trust — verify every request; PEP enforces, PDP decides
  • Auditing — log who/what/when; tamper-evident; no secrets/PII
  • Secrets — env vars/vaults, never hardcode, rotate often
