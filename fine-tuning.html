1. What Fine-Tuning Is (and Why)

Fine-tuning takes an already-trained model and keeps training it on your examples.

The core idea

A pretrained model (like a base LLM) already learned language from a huge dataset. Its knowledge lives in its weights. Fine-tuning continues that training on a smaller, focused dataset so the weights shift toward the exact behavior, style, format, or skill you want.

pretrained weights + your examples → updated weights → new behavior
The "studying before the exam" analogy: A base model is a smart student who read the whole library. Prompting is handing them a cheat sheet at the exam. Fine-tuning is making them study your specific subject beforehand — so the knowledge is internalized, not looked up in the moment.

Fine-tuning vs. prompting

 PromptingFine-tuning
Changes weights?NoYes
EffortInstant, no trainingNeeds data + a training run
Per-request costLong prompts every timeShort prompts (behavior is baked in)
Best forQuick tasks, experimentsConsistent style/format at scale
Rule of thumb: If a well-crafted prompt already works reliably, you may not need fine-tuning. Reach for fine-tuning when you need consistent behavior across thousands of calls, or a specialized skill prompting can't reach.

2. Full Fine-Tuning vs. PEFT (LoRA / QLoRA)

There are two families: retrain everything, or retrain a tiny efficient add-on.

Full fine-tuning

Every weight in the model is updated during training. This is powerful but expensive: you need enough GPU memory to hold and update billions of parameters, and you produce a full-size copy of the model for each task.

Why it's heavy: A 7-billion-parameter model has 7 billion weights to store, compute gradients for, and save. That's a lot of memory and disk for one specialized model.

Parameter-efficient fine-tuning (PEFT) — LoRA

PEFT freezes the original weights and trains only a small number of new parameters. The most popular method is LoRA (Low-Rank Adaptation):

  • Freeze the giant base model — it never changes.
  • Inject small pairs of low-rank adapter matrices (call them A and B) next to the frozen layers.
  • Only A and B are trained — often less than 1% of the total parameters.

Instead of learning a full weight update matrix ΔW (which is huge), LoRA approximates it as the product of two skinny matrices:

ΔW ≈ B · A   (A is r×k,   B is d×r,   with rank r ≪ d,k)

The final layer output uses the frozen weight plus the small learned update:

output = Wfrozen · x  +  (B · A) · x
Why LoRA is great: You train a tiny adapter (a few megabytes) instead of the whole model. Training is faster, needs far less memory, and you can swap adapters like plugins — one base model, many specialized behaviors.

QLoRA — LoRA on a small GPU

QLoRA = Quantized LoRA. It first quantizes the frozen base model (storing weights in 4-bit instead of 16-bit), which shrinks its memory footprint dramatically, then trains LoRA adapters on top.

4-bit frozen base  +  small trainable LoRA adapters → fine-tune on one consumer GPU
Why it matters: QLoRA is how people fine-tune large models on a single modest GPU. Quantization saves memory on the frozen part; LoRA keeps the trainable part tiny. The two tricks together make big-model fine-tuning affordable.

3. Preparing Your Data

Fine-tuning quality is mostly a data problem. Good data beats more data.

Instruction / response pairs

The most common format teaches the model "when you see input like this, respond like that." Each training example is a pair (often with an optional system/instruction and an input):

  • Instruction — what you want done
  • Input (optional) — the specific data to act on
  • Output — the ideal response you want the model to learn

JSONL format

JSONL = JSON Lines: one JSON object per line, no commas between lines. It is the standard for fine-tuning datasets because it streams easily.

{"messages": [{"role": "system", "content": "You are a terse SQL assistant."}, {"role": "user", "content": "Get all users created today."}, {"role": "assistant", "content": "SELECT * FROM users WHERE created_at >= CURRENT_DATE;"}]}
{"messages": [{"role": "system", "content": "You are a terse SQL assistant."}, {"role": "user", "content": "Count orders per customer."}, {"role": "assistant", "content": "SELECT customer_id, COUNT(*) FROM orders GROUP BY customer_id;"}]}

An older but common "instruction" style looks like this:

{"instruction": "Translate to formal English.", "input": "gimme the report asap", "output": "Please provide the report as soon as possible."}
{"instruction": "Translate to formal English.", "input": "no clue what happened", "output": "I am uncertain about what occurred."}

How much data — and splitting it

Dataset sizeWhat to expect
50 – 100 examplesCan nudge style/format for narrow tasks (with LoRA)
500 – 1,000 examplesA solid starting point for most behavior tuning
10,000+ examplesStronger, more reliable skills; needs careful curation

Always hold back part of your data for a validation set you never train on, so you can measure honest performance:

train ≈ 90%  ·  validation ≈ 10%
Quality > quantity: 300 clean, consistent, correctly-formatted examples beat 3,000 sloppy ones. The model imitates exactly what you show it — including your mistakes. Clean your data first.

4. The Training Process

Fine-tuning reuses the same learning loop as any neural network — just continued from a pretrained start.

The moving parts

  • Loss — measures how far the model's output is from your target response. See loss-functions.html.
  • Epochs — how many times the model sees the whole dataset. Fine-tuning usually needs few (1–4).
  • Learning rate — how big each weight update is. Fine-tuning uses a small rate so it nudges, not overwrites.
  • Batch size — how many examples per update step.

Under the hood it is the same forward pass → loss → backpropagation → weight update cycle used to train any network. For a refresher on gradients, learning rate, and overfitting see training-optimization.html.

w ← w − learning_rate × gradient
Watch for two failure modes: Overfitting (the model memorizes your examples and can't generalize — validation loss rises while training loss falls), and catastrophic forgetting (training so hard on new data that the model loses its original general abilities). Fewer epochs and a small learning rate help avoid both.

5. Fine-Tuning vs. RAG

Two different tools for two different problems. They can also be combined.

Quick comparison

 Fine-tuningRAG (retrieval)
Changes the model?Yes — updates weightsNo — adds context at query time
Best forBehavior, style, format, skillFacts, documents, changing knowledge
Update knowledgeRetrainJust update the document store
RiskOverfitting, forgettingRetrieval misses, long prompts
Decision rule: Need to change how the model responds — behavior, skill, or format? → Fine-tune. Need the model to know facts from your documents that change over time? → RAG. For the full picture on retrieval, see rag.html.

They combine well: fine-tune for the voice and format, use RAG to feed in the up-to-date facts.

6. Practical: Data + Code

A minimal, realistic example. The training code needs a GPU and libraries, so it is shown as reference.

Example training data (JSONL)

Say we want a support bot that always answers politely in exactly two sentences:

{"messages": [{"role": "user", "content": "My order is late."}, {"role": "assistant", "content": "I'm sorry your order is delayed. I've escalated it and you'll get an update within 24 hours."}]}
{"messages": [{"role": "user", "content": "How do I reset my password?"}, {"role": "assistant", "content": "You can reset it from the login page using the 'Forgot password' link. A reset email will arrive within a few minutes."}]}
{"messages": [{"role": "user", "content": "Do you ship internationally?"}, {"role": "assistant", "content": "Yes, we ship to most countries worldwide. Shipping times and fees are shown at checkout."}]}

LoRA fine-tuning with Hugging Face PEFT

Reference only: This snippet requires a GPU and the libraries transformers, peft, datasets, and trl installed. It is illustrative — not meant to be run as-is here. 
# reference-only: needs a GPU + `pip install transformers peft datasets trl`
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import LoraConfig, get_peft_model
from datasets import load_dataset
from trl import SFTTrainer, SFTConfig

base_model = "meta-llama/Llama-3.2-1B"          # a small base model

tokenizer = AutoTokenizer.from_pretrained(base_model)
model = AutoModelForCausalLM.from_pretrained(base_model)

# 1) describe the LoRA adapter (only these params are trained)
lora_config = LoraConfig(
    r=8,                    # rank of the adapter matrices (small = efficient)
    lora_alpha=16,          # scaling factor
    target_modules=["q_proj", "v_proj"],   # which layers get adapters
    lora_dropout=0.05,
    task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora_config)
model.print_trainable_parameters()   # e.g. "trainable: 0.3% of all params"

# 2) load your JSONL dataset
dataset = load_dataset("json", data_files="support_pairs.jsonl", split="train")

# 3) train (small learning rate, few epochs to avoid overfitting)
trainer = SFTTrainer(
    model=model,
    train_dataset=dataset,
    args=SFTConfig(
        output_dir="./lora-support-bot",
        num_train_epochs=3,
        per_device_train_batch_size=2,
        learning_rate=2e-4,
    ),
)
trainer.train()

# 4) save just the tiny adapter (a few MB, not the whole model)
model.save_pretrained("./lora-support-bot")

For QLoRA, you would load the base model in 4-bit (via bitsandbytes) before wrapping it with get_peft_model — same LoRA code, much less GPU memory.

Running fine-tuned models locally

Once you have a fine-tuned model (often merged and converted to GGUF), you can run it on your own machine — no GPU cloud required:

  • Ollama — write a small Modelfile that points at your model and set its behavior, then ollama create and ollama run.
  • llama.cpp — run quantized GGUF models efficiently on CPU or Apple Silicon.
# reference-only: an Ollama Modelfile
FROM ./my-finetuned-model.gguf
SYSTEM "You are a terse, polite support assistant. Answer in two sentences."
PARAMETER temperature 0.5

Then: ollama create support-bot -f Modelfile and ollama run support-bot.

7. Pitfalls to Avoid

PitfallWhat happensHow to avoid
Overfitting Model memorizes training examples; fails on new inputs. Validation loss rises. Fewer epochs, more/varied data, hold out a validation set.
Catastrophic forgetting Model loses its original general abilities after aggressive tuning. Small learning rate, few epochs, PEFT (frozen base keeps knowledge).
No evaluation You can't tell if fine-tuning actually helped. Test on a held-out set before/after; compare against the base model.
Dirty data Model imitates your inconsistencies and errors exactly. Curate for quality and consistent format first.
Always evaluate. Keep a small set of realistic test prompts. Run them through the base model and your fine-tuned model, and compare. Without evaluation you're flying blind.

Quick recap

  • Fine-tuning — continue training to change weights → new behavior
  • Full vs. PEFT — retrain everything, or train tiny LoRA adapters on a frozen base
  • QLoRA — quantize the frozen base + LoRA = fine-tune on a small GPU
  • Data — clean instruction/response pairs in JSONL; quality > quantity
  • Decision — behavior/skill/format → fine-tune; knowledge → RAG
