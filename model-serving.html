🚀 Model Serving & Deployment

Turning a trained model into a fast, reliable API — online vs batch vs streaming, FastAPI, TorchServe, Triton, vLLM, and the concepts that decide your latency and cost.

1. Training vs Inference

Two very different workloads. Serving is about inference, and it has its own rules.

Different goals, different hardware profile

Training runs the forward and backward pass over huge datasets for hours or days — it is throughput-bound and happens offline. Inference runs only the forward pass, one request at a time, and must respond in milliseconds while many users hit it at once.

 TrainingInference (Serving)
PassesForward + backwardForward only
WhenOffline, batch jobsOnline, on demand
Optimize forThroughput over daysLatency & cost per request
DataFull datasetOne or a few inputs
StateWeights changeWeights frozen
Why it matters: Because weights are frozen at inference, you can safely optimize aggressively — quantize, compile, cache, and batch — without hurting accuracy the way those tricks might hurt training.

2. Ways to Serve: Online, Batch, Streaming

Pick the pattern that matches how your users consume predictions.

Online / real-time API

A synchronous request → response over HTTP/gRPC. The client waits for the answer. Used for fraud checks, recommendations, chatbots. Optimize hard for latency.

client request → model → response (milliseconds)

Batch (offline) scoring

Score millions of rows on a schedule (e.g., nightly). No user is waiting, so you optimize for throughput and cost. Run it as a cron/Airflow job that reads a table, predicts, and writes results back.

# reference: batch scoring as a scheduled job (pseudo-CLI)
python score_batch.py \
  --input  s3://data/features/2026-09-27/ \
  --model  s3://models/churn/v3/ \
  --output s3://data/scores/2026-09-27/

Streaming

Predictions on a continuous event flow (Kafka, Kinesis, Flink). Each event is scored as it arrives — think real-time anomaly detection or live personalization. For LLMs, "streaming" also means token streaming: sending generated tokens back one at a time so the user sees text appear immediately.

  • Online — one request, wait for answer (low latency)
  • Batch — many rows, no one waiting (high throughput)
  • Streaming — unbounded event flow, score as data arrives

3. A Minimal FastAPI Serving Example

The simplest real deployment: load the model once, expose a POST /predict endpoint.

Load the model at startup, predict per request

Load weights once when the process starts (not per request), validate input with Pydantic, and return JSON. This runnable-style snippet uses a scikit-learn model, but the shape is identical for PyTorch or any framework.

# app.py  (runnable-style: pip install fastapi uvicorn scikit-learn joblib)
from fastapi import FastAPI
from pydantic import BaseModel
import joblib

app = FastAPI(title="Model Serving Demo")

# Load ONCE at import/startup, reused across all requests
model = joblib.load("model.joblib")

class Features(BaseModel):
    values: list[float]   # e.g. [5.1, 3.5, 1.4, 0.2]

@app.get("/health")
def health():
    return {"status": "ok"}

@app.post("/predict")
def predict(payload: Features):
    pred = model.predict([payload.values])[0]
    return {"prediction": int(pred)}
# run it locally
uvicorn app:app --host 0.0.0.0 --port 8000

# call it
curl -X POST http://localhost:8000/predict \
     -H "Content-Type: application/json" \
     -d '{"values": [5.1, 3.5, 1.4, 0.2]}'
Why load once? Loading weights is slow (disk + GPU transfer). Doing it per request would add seconds of latency and thrash memory. Load at startup, keep it warm.

FastAPI is perfect for small models and prototypes. For high traffic or GPUs, graduate to a purpose-built server (next section) that adds batching, model management, and metrics for you.

How a request flows through a serving stack

The load balancer spreads traffic; the batch queue groups nearby requests so the GPU processes many at once (see dynamic batching below).

4. High-Performance Serving Frameworks

When FastAPI is not enough, these servers add batching, GPU scheduling, model versioning, and metrics.

TorchServe — PyTorch models

The official PyTorch serving tool. You package weights + a handler into a .mar archive, and TorchServe exposes REST/gRPC endpoints with built-in batching, versioning, and metrics.

# reference: package and serve a PyTorch model with TorchServe
torch-model-archiver \
  --model-name resnet18 \
  --version 1.0 \
  --serialized-file resnet18.pt \
  --handler image_classifier \
  --export-path model_store

torchserve --start --model-store model_store --models resnet18=resnet18.mar
Best for: teams already on PyTorch who want a managed serving layer without writing their own API and batching logic.

NVIDIA Triton Inference Server — multi-framework, GPU-first

Serves models from PyTorch, TensorFlow, ONNX, TensorRT, and more from one server. Its standout features are dynamic batching, concurrent model execution on a single GPU, and a model-repository layout that makes versioning declarative.

# reference: Triton config.pbtxt enabling dynamic batching
name: "resnet18"
platform: "pytorch_libtorch"
max_batch_size: 32
dynamic_batching {
  preferred_batch_size: [ 8, 16, 32 ]
  max_queue_delay_microseconds: 2000
}
# reference: launch Triton pointing at a model repository (GPU)
tritonserver --model-repository=/models
Best for: mixed model zoos and heavy GPU workloads where you want maximum hardware utilization and automatic batching across frameworks.

vLLM — high-throughput LLM serving

Purpose-built for large language models. Its PagedAttention manages the attention KV-cache like OS virtual memory (pages), slashing memory waste, and continuous batching lets new requests join a running batch as older sequences finish — keeping the GPU saturated. It exposes an OpenAI-compatible API.

# reference: serve an LLM with vLLM's OpenAI-compatible endpoint (GPU)
python -m vllm.entrypoints.openai.api_server \
  --model mistralai/Mistral-7B-Instruct-v0.2 \
  --dtype auto \
  --max-model-len 8192
# call it with any OpenAI-style client
curl http://localhost:8000/v1/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "mistralai/Mistral-7B-Instruct-v0.2",
       "prompt": "Explain PagedAttention in one line:",
       "max_tokens": 64}'
Best for: serving LLMs at scale where token throughput and GPU memory efficiency dominate cost. This is the workhorse behind many self-hosted chat and RAG backends.

5. Key Concepts

The vocabulary that decides whether your service is fast, cheap, and scalable.

Latency vs Throughput

Latency = time for one request to finish (e.g., p50/p99 in milliseconds). Throughput = requests (or tokens) served per second. They pull against each other: bigger batches raise throughput but each request waits longer.

throughput ≈ batch_size ÷ batch_latency
  • Tail latency (p99) matters more than average for user experience
  • For LLMs, split into time-to-first-token and tokens/second

Dynamic & continuous batching

Dynamic batching (Triton, TorchServe) holds incoming requests for a few milliseconds and groups them so the GPU runs one big matrix multiply instead of many small ones. Continuous batching (vLLM) goes further for generation: it swaps finished sequences out and new ones in mid-flight, instead of waiting for the whole batch to complete.

Why it matters: GPUs are massively parallel — a batch of 32 often costs barely more time than a batch of 1. Batching is the single biggest lever for throughput and cost per request.

Model quantization for serving

Store and compute weights in lower precision (FP16, INT8, or 4-bit) to shrink memory and speed up inference. Because weights are frozen at serve time, a small accuracy drop is often an acceptable trade for a large speed and cost win.

PrecisionRelative sizeTrade-off
FP321×Baseline accuracy, largest
FP16 / BF16½×Near-lossless, common default
INT8¼×Fast, minor accuracy loss
4-bit (e.g. GPTQ/AWQ)⅛×Fits big LLMs on small GPUs

Autoscaling & GPU utilization

Autoscaling adds or removes replicas based on load — scale on requests-per-second or queue depth, not just CPU. GPU utilization is your efficiency scorecard: an idle GPU is wasted money, so batching, right-sizing, and packing multiple models per GPU keep it busy.

# reference: Kubernetes HPA scaling a model deployment on a custom metric
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: model-server
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: model-server
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Pods
      pods:
        metric:
          name: inference_requests_per_second
        target:
          type: AverageValue
          averageValue: "50"
  • Scale to zero for spiky/dev traffic to save GPU cost
  • Watch nvidia-smi / DCGM metrics — low utilization means batch harder or downsize
  • Keep a warm pool to avoid cold-start latency when scaling up

6. Framework Comparison

Which server for which job?

FrameworkBest forKey strength
FastAPI Prototypes, small CPU models, custom logic Simple, flexible, full control
TorchServe Production PyTorch models Managed batching, versioning, handlers
Triton Mixed frameworks, heavy GPU workloads Dynamic batching, multi-model on one GPU
vLLM High-throughput LLM / generative serving PagedAttention & continuous batching
Rule of thumb: start with FastAPI to ship; move to TorchServe/Triton when you need GPU batching and model management; reach for vLLM the moment you are serving an LLM.

7. Why This Matters for RAG & LLM Apps

Why it matters: A RAG pipeline calls a model on every user turn — usually an embedding model plus a chat LLM. If serving is slow, the whole experience feels sluggish no matter how good the retrieval is. High-throughput servers like vLLM (with continuous batching) and Triton (dynamic batching) are what make self-hosted RAG and LLM apps affordable and responsive at scale.

The pieces connect: you fine-tune a model, then serve it here, then wire the serving endpoint into a RAG app, and provision the whole stack reproducibly with MLOps & Infrastructure as Code. Serving is the bridge between a trained artifact and a product users actually touch.

  • Token streaming keeps chat UIs feeling instant even for long answers
  • Quantized LLMs let a fine-tuned model fit on cheaper GPUs
  • Autoscaling absorbs traffic spikes without over-paying at 3am
