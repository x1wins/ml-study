⚡ Hardware Acceleration: GPUs, HBM & Tensor Cores

Why GPUs crush CPUs for ML, how the memory hierarchy shapes real-world speed, and why modern deep learning is a memory-bandwidth game as much as a raw-compute game.

1. Why GPUs beat CPUs for ML

A CPU has a few very fast cores. A GPU has thousands of simpler cores. ML is embarrassingly parallel, so thousands win.

Few fast cores vs many parallel cores

A CPU is optimized for latency: run one thread as fast as possible, with big caches and branch prediction. A modern CPU has maybe 8–64 powerful cores.

A GPU is optimized for throughput: run thousands of threads at once, each doing a small piece of the same math. A data-center GPU has tens of thousands of ALUs grouped into streaming multiprocessors.

Training a neural net means multiplying huge matrices. In a matrix multiply, every output element is an independent dot product — perfect for splitting across thousands of cores.

C = A × B  ·  each Cij = Σk Aik Bkj  (all independent)
Why it matters: A CPU does the matrix multiply one small chunk at a time. A GPU launches thousands of threads that each compute a piece simultaneously, giving 10×–100× speedups on the exact workload ML needs. This connects directly to linear-algebra.html: matmul is THE operation.

See the parallelism (illustrative)

# reference: matmul is the core ML op; NumPy already uses optimized BLAS
import numpy as np

A = np.random.rand(1024, 1024).astype(np.float32)
B = np.random.rand(1024, 1024).astype(np.float32)

C = A @ B          # one call -> billions of multiply-adds, run in parallel
print(C.shape)     # (1024, 1024)

# On a GPU (illustrative, needs a CUDA device + PyTorch):
#   import torch
#   A = torch.rand(1024, 1024, device="cuda")
#   B = torch.rand(1024, 1024, device="cuda")
#   C = A @ B      # dispatched to thousands of GPU cores / Tensor Cores

The Python at the top is runnable with NumPy; the GPU block is illustrative (needs CUDA hardware).

2. The memory hierarchy: HBM, SRAM & registers

Compute is cheap; moving data is expensive. Where your numbers live decides how fast the math runs.

Fast & tiny vs slow & huge

Every level of memory trades size against bandwidth/latency. Registers and on-chip SRAM are blazing fast but tiny; HBM is large but far slower; host RAM is huge but slowest to reach across the PCIe/NVLink bus.

LevelRough sizeRough bandwidthRole
RegistersKBs per corefastest (on-chip)Operands the ALU works on right now
SRAM / shared memory (on-chip)tens of MB total~10–100 TB/sScratchpad for a tile of data being reused
HBM (high-bandwidth memory)tens of GB~1–8 TB/sThe GPU's main memory: weights, activations
Host RAM (system DRAM)hundreds of GB~0.05–0.5 TB/s over the busStaging area; slow to reach from the GPU

Numbers are order-of-magnitude and vary by generation; the ratios are what matter.

Why it matters: HBM sits on the same package as the GPU die and uses a very wide interface, which is why it delivers terabytes per second — far more than ordinary DDR system RAM. But it is still ~100× slower than on-chip SRAM. Winning at performance means keeping reused data in SRAM/registers and touching HBM as little as possible.

3. Memory-bound vs compute-bound (the roofline idea)

A kernel is limited either by how fast it can compute (FLOPs) or by how fast it can fetch data (bandwidth). Knowing which tells you what to fix.

Arithmetic intensity decides the bottleneck

Arithmetic intensity is the ratio of math done to bytes moved:

intensity = FLOPs performed ÷ bytes read+written (FLOPs/byte)
  • Low intensity (few FLOPs per byte) → memory-bound: the ALUs starve waiting on data. Examples: element-wise ops, activations, small vector adds.
  • High intensity (many FLOPs per byte) → compute-bound: the ALUs are the limit. Example: large matrix multiplies that reuse each loaded value many times.
Why it matters: If you are memory-bound, buying a chip with more FLOPs won't help — you need more bandwidth or fewer memory trips (fusion, tiling). If you are compute-bound, faster math units (Tensor Cores) or lower precision help. Modern ML speed is often a memory-bandwidth game: many real kernels are memory-bound.

4. Tensor Cores & mixed precision

Dedicated silicon that does a small matrix multiply-accumulate in one shot, at lower precision, for huge throughput.

What a Tensor Core does

A Tensor Core is a specialized unit that computes a small matrix multiply-accumulate (MMA) in a single operation — something like D = A × B + C on small tiles (e.g. 4×4 or 16×16) every cycle, instead of doing scalar multiply-adds one at a time.

D = A × B + C  ·  one fused matrix multiply-accumulate

They typically read inputs in reduced precision (FP16, BF16, or FP8) but accumulate in FP32. This is mixed precision: fast, low-precision multiplies with a high-precision running total to preserve accuracy.

Why it matters: A Tensor Core can deliver many times the matmul throughput of the general-purpose cores. Since transformers and CNNs are dominated by matmul, Tensor Cores are where most of the real training/inference speed comes from — but only if your tensors are shaped and typed so they can be used.

Mixed precision in practice (illustrative)

# illustrative: PyTorch automatic mixed precision (needs a GPU with Tensor Cores)
import torch

model  = build_model().cuda()          # your model
opt    = torch.optim.Adam(model.parameters())
scaler = torch.cuda.amp.GradScaler()   # keeps small gradients from underflowing

for x, y in loader:
    x, y = x.cuda(), y.cuda()
    opt.zero_grad()
    with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
        pred = model(x)                # matmuls run on Tensor Cores in BF16
        loss = loss_fn(pred, y)        # accumulation stays in FP32
    scaler.scale(loss).backward()
    scaler.step(opt)
    scaler.update()

Reference only — it needs CUDA hardware and a defined model. The idea: compute in low precision, keep the master weights/accumulation in FP32.

5. How matmul maps to hardware (tiling & FlashAttention)

The trick to fast matmul: load a block once, reuse it many times, and never round-trip to HBM if you can avoid it.

Tiling: reuse data in fast memory

A naive matmul streams rows and columns from HBM repeatedly — low arithmetic intensity, memory-bound. Tiling (blocking) splits the matrices into small tiles that fit in on-chip SRAM/registers, then does all the multiply-adds those tiles allow before moving on. Each value loaded from HBM gets reused many times, pushing the kernel toward compute-bound.

FlashAttention: a bandwidth-aware trick

Attention in transformers computes a big Q × KT score matrix, softmaxes it, then multiplies by V. The naive version writes that giant intermediate matrix to HBM and reads it back — classic memory-bound behavior.

FlashAttention restructures the computation to process attention in tiles that stay in on-chip SRAM, fusing the softmax so the full score matrix is never materialized in HBM. Same math, far fewer HBM round-trips → large speedups and less memory use.

Why it matters: FlashAttention is a headline example of the memory-bandwidth principle: the win comes not from more FLOPs but from avoiding data movement. Learn the attention math it optimizes in transformers.html.

6. Precision & quantization tradeoffs

Fewer bits per number means less memory, less bandwidth, and faster math — at the cost of range and accuracy.

The common formats

FormatBitsRange vs precisionTypical use
FP3232 Wide range, high precision Baseline / accumulation; "full precision"
FP1616 Good precision, narrow range (can overflow) Mixed-precision training/inference (needs loss scaling)
BF1616 Same wide range as FP32, less precision Training on modern accelerators (robust, no loss scaling)
FP88 Very small range/precision Large-model training/inference on the newest hardware
INT88 Integers via a scale factor (quantization) Inference: fast, tiny, needs calibration
FP16 vs BF16: both are 16-bit, but they split the bits differently. FP16 keeps more mantissa (precision) but a small exponent (range), so it can overflow/underflow — hence loss scaling. BF16 keeps FP32's exponent (range) with fewer mantissa bits, so it "just works" for training. FP8 pushes this further for the largest models.

Why fewer bits is faster (two reasons)

  • Bandwidth: an INT8 tensor is 1⁄4 the bytes of FP32, so it moves through HBM 4× faster — directly attacking the memory-bound bottleneck.
  • Compute: Tensor Cores hit much higher throughput at FP16/BF16/FP8/INT8 than at FP32, so the math finishes sooner too.

Quantization (e.g. FP32 → INT8) maps floats onto integers with a scale:

q = round(x ÷ scale)  ·  x ≈ q × scale

The tradeoff: smaller and faster, but rounding error can hurt accuracy, so INT8 inference usually needs calibration or quantization-aware training.

# runnable: a toy symmetric INT8 quantization round-trip with numpy
import numpy as np

x = np.array([-0.9, -0.1, 0.0, 0.4, 1.2], dtype=np.float32)

scale = np.max(np.abs(x)) / 127.0          # symmetric int8: range [-127, 127]
q = np.round(x / scale).astype(np.int8)    # quantize to integers
x_hat = q.astype(np.float32) * scale       # dequantize back to float

print("int8   :", q)
print("approx :", np.round(x_hat, 3))
print("max err:", round(float(np.max(np.abs(x - x_hat))), 4))

7. Practical: batch size, utilization & big matmuls

Getting the theoretical speed in practice is mostly about keeping the hardware busy.

Why big matmuls are efficient

Small matrices have low arithmetic intensity: you pay the fixed cost of loading data but do little math with it (memory-bound, cores idle). Big matmuls reuse each loaded tile many times, so the expensive HBM reads are amortized over lots of compute — that is when Tensor Cores run near peak.

  • Batch size: processing many samples at once turns lots of tiny matrix–vector products into one large matrix–matrix multiply, raising intensity and utilization.
  • Shapes: dimensions that are multiples of the Tensor Core tile size (often 8 or 16) let the hardware use its fast path instead of padding.
  • Utilization: the fraction of peak FLOP/s you actually achieve. Low utilization usually means memory-bound kernels, tiny batches, or awkward shapes — not a slow chip.
Rule of thumb: if the GPU is barely warm during training/inference, you are likely memory-bound or under-batched. Increase batch size, fuse element-wise ops, use mixed precision, and pick Tensor-Core-friendly shapes before reaching for a bigger GPU. When you serve models in production, these same levers drive throughput and cost — see model-serving.html.

Quick recap

  • GPUs — thousands of cores for parallel matmul, vs a CPU's few fast cores
  • Memory hierarchy — registers/SRAM (fast, tiny) → HBM (big, fast-ish) → host RAM (huge, slow)
  • Memory-bound vs compute-bound — the roofline: fix bandwidth or fix FLOPs
  • Tensor Cores — matrix multiply-accumulate units in mixed precision (FP16/BF16/FP8)
  • Tiling / FlashAttention — reuse data in SRAM, avoid HBM round-trips
  • Precision / quantization — fewer bits = less bandwidth + faster math, some accuracy risk
  • Big matmuls & batching — the way to keep the hardware fully utilized
